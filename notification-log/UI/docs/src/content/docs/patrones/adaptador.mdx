<Callout kind="concepto" title="Ficha rápida">

- **Tipo:** Adapter es GoF estructural. Anti-Corruption Layer es DDD estratégico — la misma idea aplicada a la frontera entre dos contextos.
- **Origen:** deliberado, y **verificable por compilación**: ver el recuadro de abajo.
- **Dónde:** el renderizador de plantillas, los cuatro senders y los dos consumidores de mensajería.

</Callout>

<Callout kind="codigo" title="La prueba de que esto no es decorativo">

`NotificationLog.NotificationService.Application.csproj` tiene exactamente cuatro `PackageReference` —FluentValidation y dos `Abstractions` de Microsoft— y una sola `ProjectReference`: `Domain`. **No referencia Scriban, ni `NotificationLog.Contracts`, ni EF Core.** Y `Domain.csproj` no tiene ni un `ItemGroup`.

Eso significa que "la capa de aplicación no conoce protobuf" no es una convención que alguien pueda romper por descuido: *no compila*. El adaptador no es un consejo, es la única puerta que existe.

</Callout>

## 5.1 · El problema

El flujo de envío necesita cuatro cosas que vienen de fuera: renderizar una plantilla (Scriban), hablar SMTP (`System.Net.Mail`), hablar HTTP con dos gateways, y recibir mensajes en protobuf generados por `Grpc.Tools`. Cada una tiene su propia forma, sus propios tipos y su propia semántica.

Si esos tipos entran en `Application`, tres cosas se rompen a la vez. La primera, la más obvia: cambiar de motor de plantillas o de librería de mensajería deja de ser un cambio local. La segunda: los tests de un caso de uso necesitan construir un `ScriptObject` de Scriban o un mensaje protobuf. Y la tercera, la más cara — **el modelo ajeno empieza a contagiar al propio**. El mensaje `UserContactUpdated` viene de otro contexto, con sus reglas: los campos nunca son `null` porque proto3 no lo permite, y una cadena vacía significa algo muy concreto. Si ese mensaje viaja hasta el handler, sus reglas se convierten en las nuestras sin que nadie lo haya decidido.

## 5.2 · La idea de los dos patrones

**Adapter**: nosotros escribimos la interfaz que nos conviene, y una clase la implementa traduciendo a la API ajena. El resto del sistema programa contra nuestra interfaz y nunca ve la otra. La clase adaptadora es el único sitio del código donde existe el vocabulario del tercero.

**Anti-Corruption Layer** es lo mismo, pero cuando el "tercero" es otro modelo de negocio en vez de una librería. Además de traducir tipos, traduce *significados*: decide qué quiere decir un campo vacío del otro lado en nuestro vocabulario. Sin esa capa, dos modelos que evolucionan por separado acaban acoplados por el formato del mensaje.

## 5.3 · Cómo se ve aquí

```csharp title="Application/Notifications/Services/Rendering/ITemplateRenderer.cs:7-16 (completo)"
public interface ITemplateRenderer
{
    // Cada motor de plantillas necesita sus datos en una forma distinta (diccionario plano,
    // árbol de objetos anidado, un ScriptObject de Scriban, etc.) — NotificationDispatchService no
    // interpreta ni transforma nada, solo junta evento+destinatario y reenvía lo que
    // BuildData le devuelva a Render, sin saber qué hay adentro.
    object BuildData(BusinessEvent businessEvent, Recipient recipient);

    RenderedMessage Render(string? subjectTemplate, string bodyTemplate, object data);
}
```

Este es **nuestro** contrato, escrito desde la necesidad del flujo de dispatch: dame los datos, dame el texto renderizado. No menciona Scriban. Y el comentario documenta la decisión más discutible del fichero: `BuildData` devuelve `object` a propósito, porque cada motor quiere sus datos en una forma distinta y el servicio no interpreta nada — solo pasa lo que recibe. Volveremos a ese `object` en el ejercicio.

```csharp title="Infrastructure/Notifications/Rendering/ScribanTemplateRenderer.cs:13-46"
public sealed class ScribanTemplateRenderer : ITemplateRenderer
{
    public object BuildData(BusinessEvent businessEvent, Recipient recipient)
    {
        var recipientData = new ScriptObject
        {
            ["id"] = recipient.Id,
            ["name"] = recipient.Name,
            ["email"] = recipient.Email,
            ["phone"] = recipient.Phone,
            ["locale"] = recipient.Locale,
            ["timeZone"] = recipient.TimeZone
        };

        foreach (var (key, value) in recipient.Attributes)
            recipientData[key] = value;

        var root = new ScriptObject { ["recipient"] = recipientData };

        foreach (var (key, value) in businessEvent.Data)
            root[key] = value;

        return root;
    }

    public RenderedMessage Render(string? subjectTemplate, string bodyTemplate, object data)
    {
        var globals = (ScriptObject)data;

        var body = RenderTemplate(bodyTemplate, globals);
        var subject = subjectTemplate is null ? null : RenderTemplate(subjectTemplate, globals);

        return RenderedMessage.Create(subject, body);
    }
    // ... RenderTemplate: Template.Parse + TemplateContext { StrictVariables = true }
}
```

Los papeles:

- **El cliente** es `NotificationDispatchService`, que solo ve `ITemplateRenderer`.
- **La abstracción (*target*)** es `ITemplateRenderer`, y vive en `Application`.
- **El adaptador** es `ScribanTemplateRenderer`, en `Infrastructure`.
- **El adaptado (*adaptee*)** son `Template`, `TemplateContext` y `ScriptObject`, de Scriban. Estos tres nombres aparecen **únicamente** en este fichero.

Y el adaptador hace lo que hacen los buenos adaptadores: no traduce solo tipos, **traduce modelos**. La línea 30 construye un árbol anidado —`recipient` como sub-objeto, los datos del evento en la raíz— porque Scriban resuelve `{{ recipient.name }}` navegando miembros, no buscando una clave con un punto dentro. Esa peculiaridad del motor queda encerrada aquí; el servicio de dispatch nunca se entera de que existe.

### La versión ACL: los consumidores de mensajería

```csharp title="Infrastructure/Messaging/Consumers/UserContactUpdatedHandler.cs:6-27 (completo)"
public static class UserContactUpdatedHandler
{
    public static Task Handle(UserContactUpdated message, RecipientSyncService syncService, CancellationToken ct)
    {
        var change = MapToUserChange(message); // Protobuf -> el UserChange de Application
        return syncService.HandleAsync(change, ct);
    }

    // email/phone vacíos ya son un valor con significado (sin dato confirmado), no "no vino" —
    // el mensaje es un snapshot completo, así que se pasan tal cual, sin traducir "" a null. Mismo
    // criterio para attributes: una clave ausente del map ya significa "ya no la tiene".
    private static UserChange MapToUserChange(UserContactUpdated message) =>
        new(
            UserId: Guid.Parse(message.UserId),
            Name: message.Name,
            Email: message.Email,
            Phone: message.Phone,
            Locale: message.Locale,
            TimeZone: message.TimeZone,
            Attributes: message.Attributes.ToDictionary(kv => kv.Key, kv => (string?)kv.Value),
            IsActive: message.IsActive);
}
```

Una clase estática de doce líneas. Su único trabajo es que `UserContactUpdated` —el tipo generado por protobuf— muera aquí y siga `UserChange`, un `record` de `Application` (`Recipients/Services/Sync/UserChange.cs:3`).

Fíjate en el comentario de las líneas 14-16: no describe qué hace el código, **declara una decisión semántica**. En el modelo de origen una cadena vacía significa "no hay valor confirmado", no "no ha cambiado" —el mensaje es un snapshot completo—, así que se traslada tal cual sin convertirla en `null`. Esa decisión es exactamente el trabajo de un ACL, y su consecuencia se ve tres capas más allá: `UpdateRecipientHandler.cs:25-35` aplica cada campo siempre, sin preguntarse si "vino o no vino".

## 5.4 · Recorrido de una ejecución

Un mensaje `UserContactUpdated` llega a la cola `user-changes` con `phone = ""` — el usuario borró su teléfono en el sistema de origen.

<ol class="ddd-steps">
    <li>
        <strong><code>Infrastructure/Messaging/RabbitMq/RabbitMqMessagingExtensions.cs:47-48</code></strong> —
        la cola está fijada a <code>UserContactUpdated</code> con
        <code>DefaultIncomingMessage&lt;T&gt;()</code>. Wolverine elige el deserializador según el
        <code>content_type</code> AMQP (líneas 43-45): protobuf por defecto, JSON si el mensaje se publicó a

    </li>

        <code>recipient.ChangePhone(cmd.Phone)</code> con <code>""</code>. El dominio aplica su propia regla
        en <code>Recipient.NormalizePhone</code> (<code>Recipient.cs:121-122</code>): vacío se normaliza a
        <code>null</code>. El teléfono queda borrado, que era la intención del mensaje.
    </li>
    <li>
        <strong>Efecto observable</strong> — <code>recipient.CanReceive(NotificationChannel.Sms)</code>
        (<code>Recipient.cs:66</code>) pasa a devolver <code>false</code>, y a partir del siguiente evento el
        canal SMS de este destinatario se salta con un aviso en
        <code>NotificationDispatchService.cs:90-93</code>. Nada de eso conoce protobuf.
    </li>
</ol>

<Callout kind="concepto" title="Tres modelos para el mismo dato, y no sobra ninguno">

`UserContactUpdated` (contrato entre sistemas, versionable, no lo controlamos del todo) → `UserChange` (nuestro vocabulario de entrada) → `UpdateRecipientCommand` (la intención de un caso de uso) → `Recipient` (el modelo con las reglas).

Parece repetición, y es lo contrario: cada salto es un punto donde el cambio del otro lado se puede absorber sin propagarse. Si mañana el contrato añade un campo o parte `name` en dos, se toca *un* fichero de traducción.

</Callout>

## 5.5 · Qué pasaría sin el patrón

Contraejemplo **hipotético**: el mensaje entra tal cual.

```csharp title="Hipotético — sin capa de traducción"
// HIPOTÉTICO — así NO está el código
public sealed class RecipientSyncService
{
    // el tipo generado por protobuf, dentro de la capa de aplicación
    public async Task HandleAsync(UserContactUpdated message, CancellationToken ct)
    {
        var userId = Guid.Parse(message.UserId);

        // proto3 no tiene null: hay que razonar sobre "" en todas partes
        var email = string.IsNullOrEmpty(message.Email) ? null : message.Email;
        var phone = string.IsNullOrEmpty(message.Phone) ? null : message.Phone;

        // ... y este "?" ya no es una decisión nuestra, es una consecuencia del formato ajeno
    }
}
```

Lo que se rompe:

- **`Application` tiene que referenciar `NotificationLog.Contracts`**, y con él `Google.Protobuf`. La capa de casos de uso pasa a depender de un formato de serialización.
- **Las reglas de proto3 se cuelan en el dominio.** Los campos generados nunca son `null`, así que el handler tiene que razonar sobre cadenas vacías en todas partes, y la distinción entre "vacío" y "ausente" —que en el modelo propio sí existe— se pierde.
- **Cambiar el contrato obliga a tocar casos de uso.** Renombrar un campo del `.proto` rompe la compilación de `Application`, no de una clase de traducción.
- **Los tests necesitan construir mensajes protobuf** para probar una regla de negocio.

**Qué se paga:** un `record` extra por mensaje y un método de mapeo que hay que mantener sincronizado a mano. Cuando el contrato y el modelo interno son casi idénticos —como aquí— parece código duplicado, y es la queja habitual. La respuesta es que *hoy* se parecen; el adaptador existe para el día en que dejen de parecerse, que es el día en que un cambio ajeno intentará entrar.

## 5.7 · Señales de alarma

- **Un `using` nuevo en `Application`.** La forma más rápida de auditar esta capa es mirar su `.csproj`: cuatro paquetes y una referencia. Cualquier adición merece justificación explícita en la revisión.
- **Un adaptador que crece con lógica de negocio.** Si `MapToUserChange` empieza a decidir *qué hacer* con los datos en vez de solo traducirlos, el negocio se ha mudado a `Infrastructure`.
- **Excepciones del tercero escapando del adaptador.** Un `ScriptRuntimeException` de Scriban que llegue al llamante convierte el puerto en decorativo. Aquí no ocurre por casualidad: `NotificationDispatchService.cs:113` captura `Exception` genérica alrededor del renderizado, así que el tipo concreto nunca se inspecciona.
- **Un puerto que se parece sospechosamente a la API del tercero.** Si `ITemplateRenderer` tuviera un método `PushGlobal`, no sería un puerto: sería Scriban con otro nombre.
- **`object` en la firma de un puerto.** Está aquí y es el tema del ejercicio.
