## 6.1 · El problema

Una notificación se envía por Email, SMS, Push o WhatsApp. La operación es conceptualmente la misma —"llévale este texto a esta dirección"— pero cada canal habla con un proveedor distinto: SMTP para correo, un gateway REST para SMS, otro REST distinto para push, y WhatsApp todavía sin proveedor elegido.

El servicio de dispatch no debe saber nada de eso. Su trabajo es recorrer las configuraciones activas de un trigger y, para cada una, renderizar y enviar. Si dentro de ese bucle apareciera un `SmtpClient`, la capa de aplicación quedaría atada a una librería de correo y añadir un canal significaría reescribir el flujo de negocio.

## 6.2 · La idea del patrón

Se define **una** abstracción para la operación que varía, y una implementación por cada forma de hacerla. El código que la usa depende solo de la abstracción y recibe la implementación concreta desde fuera; nunca la elige con un condicional sobre un tipo.

La palabra importante es *una*. El valor del patrón no está en tener varias implementaciones —eso se consigue con cualquier interfaz—, sino en que el cliente **no sepa cuántas hay**. Si el cliente tiene que enumerarlas para elegir, el polimorfismo no está haciendo su trabajo y el patrón se ha quedado a mitad.

## 6.3 · Cómo se ve aquí

```csharp title="Application/Notifications/Services/Sending/ — cuatro ficheros, cuatro interfaces"
// IEmailNotificationSender.cs
public interface IEmailNotificationSender
{
    Task<NotificationSendResult> SendAsync(string destination, RenderedMessage message, CancellationToken ct);
}

// ISmsNotificationSender.cs
public interface ISmsNotificationSender
{
    Task<NotificationSendResult> SendAsync(string destination, RenderedMessage message, CancellationToken ct);
}

// IPushNotificationSender.cs
public interface IPushNotificationSender
{
    Task<NotificationSendResult> SendAsync(string destination, RenderedMessage message, CancellationToken ct);
}

// IWhatsAppNotificationSender.cs
public interface IWhatsAppNotificationSender
{
    Task<NotificationSendResult> SendAsync(string destination, RenderedMessage message, CancellationToken ct);
}
```

Cuatro interfaces con **la misma firma exacta**. No hay una interfaz base, ni un tipo común, ni nada que las relacione: para el compilador son cuatro contratos independientes que casualmente se parecen.

Y la consecuencia inmediata está en el cliente:

```csharp title="Application/…/Dispatch/NotificationDispatchService.cs:164-173 (completo)"
    private Task<NotificationSendResult> SendAsync(
        NotificationChannel channel, string destination, RenderedMessage message, CancellationToken ct)
        => channel switch
        {
            NotificationChannel.Email => _emailSender.SendAsync(destination, message, ct),
            NotificationChannel.Sms => _smsSender.SendAsync(destination, message, ct),
            NotificationChannel.Push => _pushSender.SendAsync(destination, message, ct),
            NotificationChannel.WhatsApp => _whatsAppSender.SendAsync(destination, message, ct),
            _ => throw new InvalidOperationException($"El canal '{channel}' no tiene un remitente registrado.")
        };
```

Diagnóstico, pieza a pieza:

- **Lo que sí es Strategy:** el algoritmo de envío está encapsulado fuera del servicio, detrás de una interfaz, y la implementación concreta llega por inyección. Cambiar el proveedor de SMS es cambiar una clase de `Infrastructure` y nada más. Eso funciona y es valioso.
- **Lo que falta:** la *selección*. Un Strategy completo recibe la estrategia ya elegida; aquí el cliente enumera las cuatro y decide con un `switch` sobre un `enum`. Es exactamente el condicional que el patrón existe para eliminar.
- **La rama `_`:** `throw new InvalidOperationException("...no tiene un remitente registrado.")`. Esa rama es la confesión del problema — existe porque el compilador *no puede* garantizar que todos los canales estén cubiertos.

El coste se ve mejor en el constructor:

```csharp title="NotificationDispatchService.cs:31-46 (constructor)"
    public NotificationDispatchService(
        INotificationTriggerRepository triggers,
        IRecipientRepository recipients,
        INotificationTemplateRepository templates,
        ITemplateRenderer renderer,

        IPushNotificationSender pushSender,

        => (_triggers, _recipients, _templates, _renderer, _emailSender, _smsSender, _pushSender,
            _whatsAppSender, _recordSuccess, _recordFailure, _log)

               whatsAppSender, recordSuccess, recordFailure, log);
```

Once parámetros, de los cuales **cuatro son la misma dependencia repetida**. Y hay una víctima colateral concreta: como el constructor exige las cuatro interfaces, WhatsApp —que no tiene proveedor— necesita una implementación para que el contenedor pueda construir el servicio. De ahí sale esta clase:

```csharp title="Infrastructure/Notifications/Sending/WhatsApp/NotImplementedWhatsAppNotificationSender.cs:6-14 (completo)"
// Sin proveedor de WhatsApp elegido todavía. Este stub existe únicamente para que
// NotificationDispatchService pueda registrarse en el contenedor — su constructor pide las cuatro
// interfaces de envío — y revienta siempre a propósito: un mensaje de WhatsApp que "se envía" en
// silencio sería peor que uno que queda registrado como notificación fallida con el motivo exacto.
public sealed class NotImplementedWhatsAppNotificationSender : IWhatsAppNotificationSender
{
    public Task<NotificationSendResult> SendAsync(string destination, RenderedMessage message, CancellationToken ct)
        => throw new NotSupportedException("IWhatsAppNotificationSender todavía no tiene una implementación real.");
}
```

El comentario es honesto y la decisión de lanzar —en vez de fingir un envío— es **correcta**: un mensaje que "se envía" en silencio sería peor que uno registrado como fallido con su motivo (y el `catch` de `NotificationDispatchService.cs:150` lo convierte justo en eso). Pero fíjate en la primera frase: *"este stub existe únicamente para que NotificationDispatchService pueda registrarse en el contenedor"*. La clase no existe por una necesidad del dominio, existe **para satisfacer una firma**. Es deuda del diseño, no del negocio.

## 6.5 · Qué pasaría sin el patrón, y qué pasaría con él completo

### Sin ningún patrón

```csharp title="Hipotético — el proveedor dentro del servicio de aplicación"
// HIPOTÉTICO — así NO está el código
private async Task<NotificationSendResult> SendAsync(
    NotificationChannel channel, string destination, RenderedMessage message, CancellationToken ct)
{
    if (channel == NotificationChannel.Email)
    {
        using var mail = new MailMessage(_from, destination) { Subject = message.Subject, Body = message.Body };
        using var client = new SmtpClient(_host, _port);
        await client.SendMailAsync(mail, ct);
        return NotificationSendResult.Success(null);
    }

    if (channel == NotificationChannel.Sms)
    {
        var response = await _http.PostAsJsonAsync(_smsPath, new { to = destination, message = message.Body }, ct);
        // ...
    }
    // ...
}
```

`Application` pasaría a depender de `System.Net.Mail` y de `HttpClient`, probar el flujo de dispatch exigiría un servidor SMTP, y cambiar de proveedor de SMS sería un cambio en la capa de negocio. **Lo que hay hoy es claramente mejor que esto**: el mérito de las cuatro interfaces es real, y conviene decirlo antes de criticar lo que falta.

### Con el patrón completo

La corrección es pequeña: **una** interfaz, que además declara a qué canal sirve.

```csharp title="Propuesta — una abstracción y una resolución por clave"
// Application/Notifications/Services/Sending/INotificationSender.cs
public interface INotificationSender
{
    NotificationChannel Channel { get; }

    Task<NotificationSendResult> SendAsync(string destination, RenderedMessage message, CancellationToken ct);
}

// y en el servicio, sin switch:
private readonly IReadOnlyDictionary<NotificationChannel, INotificationSender> _senders;

public NotificationDispatchService(/* ... */ IEnumerable<INotificationSender> senders /* ... */)
    => _senders = senders.ToDictionary(s => s.Channel);

private Task<NotificationSendResult> SendAsync(
    NotificationChannel channel, string destination, RenderedMessage message, CancellationToken ct)
    => _senders[channel].SendAsync(destination, message, ct);
```

Lo que se gana:

- **El constructor baja de once a ocho parámetros**, y añadir un canal ya no lo toca.
- **El `switch` desaparece**, y con él la rama `_` imposible de verificar. El fallo "no hay sender para este canal" pasa de ser una excepción en mitad de un envío a ser una comprobación que se puede hacer *al arrancar*.
- **El stub de WhatsApp deja de ser obligatorio.** Puede seguir existiendo —la decisión de lanzar en vez de fingir sigue siendo buena— pero por elección, no porque una firma lo exija.
- **Añadir un canal son tres ediciones** en vez de seis, y ninguna en `Application`.

**Qué se paga:** la resolución deja de ser estática. Con el `switch`, cualquiera ve de un vistazo qué implementación atiende cada canal; con el diccionario hay que mirar el registro en DI. También hay un riesgo nuevo: dos senders declarando el mismo `Channel`, que el `ToDictionary` convertiría en una excepción de arranque — ruidosa, pero de arranque, que es justo cuando quieres enterarte.

## 6.6 · Otras apariciones del mismo `switch` en el repositorio

| Sitio | ¿Es el mismo problema? |
| --- | --- |
| `Domain/Recipients/Recipient.cs:59-64` — `AddressFor` | **No, y está bien así.** Es un mapeo de canal a dato, no una selección de comportamiento: no hay nada polimórfico que extraer. Convertirlo en cuatro clases sería sobreingeniería. Eso sí, es el *segundo* sitio que hay que tocar al añadir un canal. |
| `Domain/Templates/TemplateVersion.cs:35` — `requiresSubject` | **No.** Un `is Email or Push` de una línea que expresa una regla de negocio ("solo estos canales tienen asunto"). Una jerarquía de clases por canal aquí oscurecería una regla que hoy se lee de un vistazo. |
| `ApiService/Exceptions/GlobalExceptionHandler.cs:18-37` | **Es discutible, y hoy no duele.** Un `switch` sobre tipos de excepción es el olor clásico que pide polimorfismo, pero aquí concentra *a propósito* todo el contrato de errores de la API en un sitio legible. Crece muy despacio (tres tipos en toda la vida del proyecto) y el traductor no debe vivir en las excepciones, que están en capas que no conocen HTTP. |
| `Web/Components/Ddd/DddCallout.razor:11-20` | **No.** Un `switch` de presentación que asocia un icono a un tipo de recuadro. Ni negocio ni comportamiento. |

<Callout kind="concepto" title="La regla para distinguirlos">

Un `switch` pide Strategy cuando **cada rama hace algo distinto** —invoca otro colaborador, ejecuta otro algoritmo— y cuando la lista de ramas va a crecer. Un `switch` que solo *elige un dato* y vive dentro del tipo dueño de ese dato no pide nada: convertirlo en clases añade ficheros y no elimina el acoplamiento al `enum`.

</Callout>

## 6.7 · Señales de alarma

- **Varias interfaces con la misma firma.** Es la señal que define este caso. Si cuatro contratos son idénticos salvo por el nombre, el tipo común que falta es la abstracción del patrón.
- **Una rama `default` que lanza.** Casi siempre significa que el compilador no puede comprobar algo que el diseño da por cierto.
- **Dependencias inyectadas y no usadas en la mayoría de las ejecuciones.** En cada envío se construyen cuatro senders —dos de ellos con su `HttpClient`— y se usa uno.
- **Una implementación que existe solo para que el contenedor arranque.** `NotImplementedWhatsAppNotificationSender` es el ejemplo, y el comentario lo admite.
- **El mismo `enum` repartido en varios `switch`.** Hoy son dos (`SendAsync` y `AddressFor`); en cuanto sean cuatro, olvidar uno al añadir un canal deja de ser una posibilidad y pasa a ser una certeza.
- **Un Strategy que se degrada al revés.** Ojo también con la dirección contraria: si alguien "arregla" esto metiendo `if` por canal *dentro* de un sender único, se habrá cambiado un problema visible por uno escondido.
