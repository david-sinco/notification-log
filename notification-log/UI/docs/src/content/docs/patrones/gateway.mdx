<p class="ddd-lede">
El panel tiene veinte páginas y ninguna base de datos. Todo lo que muestra llega por HTTP desde tres
APIs distintas. Si cada página construyera su propia petición, la aplicación tendría veinte sitios
donde se escribe una ruta a mano, veinte sitios donde se decide qué hacer con un <code>404</code> y
veinte sitios que hay que tocar cuando un endpoint cambia de forma.
</p>

En lugar de eso hay nueve clases en medio, y las páginas no saben que existe el protocolo HTTP.

<div class="ddd-frase">
<strong>En una frase:</strong> un gateway es un adaptador con una responsabilidad extra — además de
envolver la tecnología, <strong>traduce el idioma de la red al idioma de la aplicación</strong>:
rutas a métodos, y códigos de estado a excepciones con significado.
</div>

## Ya conoces la pieza: es la centralita de una oficina

Nadie marca la extensión de contabilidad. Llamas a la centralita y pides *"con contabilidad, por favor"*. Si mañana cambian el número, lo sabe la centralita y nadie más se entera.

Y hace algo que no es solo redirigir: **traduce las respuestas**. Cuando la línea está ocupada no te devuelve un tono raro, te dice *"está comunicando, ¿quiere esperar?"*. Convierte el estado técnico de la red en algo sobre lo que puedes decidir.

<Callout kind="advertencia" title="Dónde falla la analogía">

Una centralita pasa la llamada tal cual. Un gateway **cambia la forma**: recibe un `404` y lanza una excepción; recibe JSON y devuelve un objeto de la aplicación. No es un tubo, es un traductor.

Y hay algo que la centralita no hace: aquí el gateway **añade la identidad del que llama** en cada petición, sin que la página lo pida ni se entere. Es la cuarta idea.

</Callout>

`DraftAsync`, `ChangePriceAsync`, `SubmitForReviewAsync`. Ninguna página construye una URL ni elige un verbo HTTP: llaman a un método y reciben un objeto.

Hay nueve de estos, uno por familia de recursos: publicaciones, moderación, visitas, propietarios, usuarios, disparadores, plantillas, destinatarios y envíos.

**Por qué importa:** cuando una ruta cambia hay **un** archivo que tocar. Sin esta capa, la ruta estaría repetida en cada página que la usa y cambiarla sería una búsqueda de texto con la esperanza de no olvidar ninguna.

La API devuelve errores en formato **ProblemDetails**: un JSON con título, detalle y —en las validaciones— los errores agrupados por campo. Este método lo lee **una sola vez para todo el panel** y lo convierte en una excepción tipada.

A partir de ahí las páginas ya no tratan con códigos HTTP: capturan `ApiException`, muestran el mensaje en un aviso, y si trae errores por campo los reparten por el formulario.

**Por qué importa:** el `422` que devuelve la API cuando una regla de negocio dice que no lleva el mensaje escrito en el agregado, en español. Gracias a esta traducción, ese texto llega intacto a la pantalla del usuario sin que ninguna página sepa qué es un 422.

Fíjate también en el `catch (JsonException)` vacío: si el cuerpo no es un ProblemDetails —un `500` sin cuerpo, un proxy que devuelve HTML— la excepción se lanza igual, con un mensaje genérico. **El gateway nunca deja pasar un fallo en silencio.**

## Idea 4 · Y añade lo que la página no debería tener que recordar

<Code
    code={whole(tokenHandler)}
    lang="csharp"
    title="Web · Authentication/AccessTokenHandler.cs"
/>

Doce líneas que ponen la cabecera `Authorization` en cada petición saliente. No se llama desde ninguna página: se engancha al `HttpClient` en el arranque.

Y en el arranque del panel se ve una decisión: **solo los clientes que llaman a APIs protegidas** lo llevan.

| Cliente tipado | Destino | ¿Lleva token? |
| --- | --- | --- |
| `UsersApiClient` | Identity | **Sí** |
| `OwnersApiClient`, `ListingsApiClient`, `ModerationApiClient` | Rentals | **Sí** |
| `VisitsApiClient` | Rentals | No — las visitas aún reciben el actor en el cuerpo |
| `TriggersApiClient`, `TemplatesApiClient`, `RecipientsApiClient`, `NotificationsApiClient` | Notifications | No — esa API todavía no valida tokens |

Las dos últimas filas no son decisiones de diseño: son deudas, y están documentadas como tales en [Arquitectura](/arquitectura/decisiones).

**Por qué importa:** es la responsabilidad extra que convierte un adaptador en un gateway. La identidad, los reintentos y el descubrimiento de servicios se aplican **a todas las llamadas**, y ninguna página participa en ello.

## El recorrido: aprobar una publicación desde el panel

<ol class="ddd-steps">
    <li>La página llama a <code>ModerationApiClient.ReviewAsync(id, ...)</code>. No sabe qué ruta es.</li>
    <li>El cliente construye la petición y la manda por su <code>HttpClient</code>.</li>
    <li><strong>El manejador de token</strong> añade la cabecera de autorización.</li>
    <li><strong>El manejador de resiliencia</strong> —que pone <code>ServiceDefaults</code> sin que nadie lo pida— aplica tiempos de espera y reintentos.</li>
    <li><strong>El descubrimiento</strong> traduce <code>rental</code> a una dirección real.</li>
    <li>La API responde. Si es <code>2xx</code>, se deserializa y vuelve como objeto.</li>
    <li>Si no, <code>EnsureSuccessAsync</code> lee el ProblemDetails y lanza <code>ApiException</code>, que la página muestra en un aviso.</li>
</ol>

De los siete pasos, la página escribe **el primero**. Los demás los pone la composición del arranque.

## Qué pasaría sin el patrón

Contraejemplo **hipotético**, dentro de una página Blazor:

```razor
@* HIPOTÉTICO — así NO está el código *@
@inject HttpClient Http

@code {
    async Task Aprobar(Guid id)
    {
        var response = await Http.PostAsJsonAsync($"https://localhost:7057/api/moderation/{id}/review",
            new { decision = "Approved" });
        if (!response.IsSuccessStatusCode)
            error = "Algo salió mal";   // y el mensaje del dominio se pierde aquí
    }
}
```

Lo que se rompe: **el puerto aparece en una página** y deja de poder resolverse por nombre; **el mensaje de negocio se pierde**, porque nadie lee el ProblemDetails; **el token no viaja**, así que la llamada falla con 401 y alguien acabará copiando la cabecera a mano en cada página; y la ruta queda repetida tantas veces como páginas la usen.

**Lo que se paga a cambio:** nueve clases y sus modelos, y una indirección entre la página y la llamada. Para un panel con dos pantallas sería demasiado; con veinte, se amortiza en la primera ruta que cambia.

## Lo que suele confundir

<Callout kind="antipatron" title="Cuatro malentendidos sobre el gateway">

**"Es lo mismo que un Repository."** Se parecen en la forma —los dos esconden de dónde vienen los datos— y se diferencian en dónde viven y qué protegen. El repositorio protege **al dominio** de la persistencia; el gateway protege **a la interfaz de usuario** de la red. Uno vive en el servidor de negocio, el otro en el cliente.

**"Los modelos del panel duplican los DTO de la API."** Es deliberado. Lo que cruza es JSON, no tipos: si el panel referenciara los DTO de la API, un cambio interno de un servicio recompilaría la interfaz, y dos procesos que se despliegan por separado tendrían que desplegarse juntos.

**"El gateway debería reintentar cuando falla."** Ya se reintenta, pero no aquí: lo pone el manejador de resiliencia común. Meter reintentos dentro del cliente tipado sería duplicar esa política y esconderla.

**"Como Blazor Server corre en el servidor, esto es una llamada local."** No: es una llamada HTTP entre dos procesos, con su latencia y sus fallos. Lo que sí es cierto es que **sale del servidor, no del navegador** — por eso las APIs no necesitan CORS para el panel.

</Callout>

## Lo que esta ficha deja fuera

- **De dónde sale el token** y cómo se obtiene: [Arquitectura · Identidad](/arquitectura/identidad).
- **La resiliencia común** y el descubrimiento por nombre: [Arquitectura · HTTP](/arquitectura/http).
- **La comunicación entre servicios**, que no usa este patrón en absoluto: ningún servicio llama a otro por HTTP, todo va por mensajes.
- **El API Gateway** de arquitectura distribuida —un proceso separado que enruta—, que es otro patrón con nombre parecido y no está aquí.

<Callout kind="resumen" title="Para recordar">

- Nueve clientes tipados: **las páginas nunca ven un `HttpClient`** ni escriben una ruta.
- La dirección de cada servicio aparece **una vez**, y es un nombre, no un puerto.
- El gateway **traduce el protocolo**: ProblemDetails entra, `ApiException` sale, y el mensaje del dominio llega intacto a la pantalla.
- Nunca deja pasar un fallo en silencio, ni siquiera cuando el cuerpo no se puede leer.
- Añade **token, reintentos y descubrimiento** a todas las llamadas, sin que la página participe.
- El panel tiene **sus propios modelos**: lo que cruza es JSON, no tipos.

</Callout>
