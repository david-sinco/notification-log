<Callout kind="concepto" title="Ficha rápida">

- **Tipo:** arquitectónico (Fowler: *Gateway* / *Remote Facade*). Es un Adapter con un propósito concreto: encapsular el acceso a un sistema externo.
- **Origen:** deliberado en el diseño, aunque el mecanismo —*typed clients* de `IHttpClientFactory`— lo facilita el framework.
- **Dónde:** los cuatro `NotificationLog.Web/Api/*/…ApiClient.cs`, más el trío de apoyo `ApiResponseExtensions`, `ApiException` y `QueryString`.

</Callout>

## 7.1 · El problema

`NotificationLog.Web` y `NotificationLog.ApiService` son **dos procesos distintos**. El panel no comparte base de datos ni memoria con la API: le habla por HTTP. Eso significa que cada listado, cada formulario y cada botón de la interfaz implica construir una URL, montar una cadena de consulta, serializar un cuerpo, mirar el código de estado y deserializar la respuesta.

Si eso vive en las páginas, cada componente `.razor` acaba con seis líneas de fontanería HTTP antes de poder pintar una tabla. Peor: cada uno decide a su manera qué hacer con un 404 o un 422, y las opciones de JSON se repiten en veinte sitios hasta que uno se desvía.

Y hay un problema añadido y específico de este proyecto: el panel **no puede** reutilizar los DTO del servidor. `NotificationLog.Web.csproj` tiene una sola `ProjectReference`, a `ServiceDefaults`; no referencia ni `Application` ni `Domain`. Así que alguien tiene que decidir dónde viven los tipos de la conversación.

## 7.2 · La idea del patrón

Se crea un objeto por cada sistema externo con el que se habla, y se le da **métodos en el vocabulario del que llama**, no en el del protocolo. El cliente pide `ListAsync(search, isEnabled, page, pageSize)` y recibe objetos; lo que hay debajo —HTTP, JSON, códigos de estado— queda dentro.

Un Gateway aporta dos cosas más que un simple envoltorio: es el sitio donde el modelo de errores del sistema externo se traduce al propio, y es el sitio donde se puede sustituir el sistema entero por un doble en los tests, porque los llamantes dependen de una clase que se puede reemplazar.

## 7.3 · Cómo se ve aquí

```csharp title="NotificationLog.Web/Program.cs:17-22"
// Clientes tipados hacia NotificationLog.ApiService. La URL usa "https+http://" para preferir
// HTTPS cuando esté disponible; la resuelve el descubrimiento de servicios de Aspire.
builder.Services.AddHttpClient<TriggersApiClient>(client => client.BaseAddress = new("https+http://apiservice"));
builder.Services.AddHttpClient<TemplatesApiClient>(client => client.BaseAddress = new("https+http://apiservice"));
builder.Services.AddHttpClient<RecipientsApiClient>(client => client.BaseAddress = new("https+http://apiservice"));
builder.Services.AddHttpClient<NotificationsApiClient>(client => client.BaseAddress = new("https+http://apiservice"));
```

`AddHttpClient<T>` es el mecanismo de *typed client*: registra la clase y le inyecta un `HttpClient` ya configurado, con su gestión de conexiones resuelta por `IHttpClientFactory`. La dirección `https+http://apiservice` no es una URL real: es un nombre lógico que el descubrimiento de servicios de Aspire resuelve en ejecución. **Ninguna página conoce un puerto ni un host.**

```csharp title="NotificationLog.Web/Api/Triggers/TriggersApiClient.cs:5-34 (extracto)"
public sealed class TriggersApiClient(HttpClient http)
{
    public async Task<PagedResult<TriggerSummaryDto>> ListAsync(
        string? search, bool? isEnabled, int page, int pageSize, CancellationToken ct)
    {
        var query = QueryString.Build(
            ("search", search),
            ("isEnabled", isEnabled?.ToString()),
            ("page", page.ToString()),
            ("pageSize", pageSize.ToString()));

        var response = await http.GetAsync($"/api/triggers{query}", ct);
        await response.EnsureSuccessAsync(ct);
        return (await response.Content.ReadFromJsonAsync<PagedResult<TriggerSummaryDto>>(ApiJson.Options, ct))!;
    }

    public async Task<Guid> CreateAsync(CreateTriggerRequest request, CancellationToken ct)
    {
        var response = await http.PostAsJsonAsync("/api/triggers", request, ApiJson.Options, ct);
        await response.EnsureSuccessAsync(ct);
        var body = await response.Content.ReadFromJsonAsync<CreatedResponse>(ApiJson.Options, ct);
        return body!.Id;
    }

    // ... SetStatusAsync, UpdateDescriptionAsync, AddConfigurationAsync,
    //     DisableConfigurationAsync, EnableConfigurationAsync, ChangeConfigurationTemplateAsync
}
```

Los papeles:

- **El cliente** es la página `.razor`, que solo ve `TriggersApiClient`.
- **El Gateway** es la clase: nueve métodos que son casi la única superficie de la API que el panel conoce.
- **El sistema externo** es `ApiService`, y el detalle de cómo se le habla —rutas, verbos, forma del cuerpo— está encerrado aquí.
- **El patrón de tres líneas** se repite en los treinta y tantos métodos de los cuatro clientes: llamar, `EnsureSuccessAsync`, deserializar. Es repetición deliberada y legible; intentar abstraerla en un método genérico `SendAsync<TReq,TRes>` costaría más claridad de la que ahorraría.

### La pieza que hace de traductor de errores

```csharp title="Web/Api/ApiResponseExtensions.cs:6-27 (completo) y Web/Api/ApiException.cs:5-15"
// Web/Api/ApiResponseExtensions.cs
internal static class ApiResponseExtensions
{
    // El ApiService devuelve ProblemDetails/ValidationProblemDetails en los errores (404, 400, 422).
    // Si el cuerpo no es JSON parseable (p. ej. un 500 sin cuerpo), se degrada a un mensaje genérico.
    public static async Task EnsureSuccessAsync(this HttpResponseMessage response, CancellationToken ct)
    {
        if (response.IsSuccessStatusCode)
            return;

        ProblemPayload? problem = null;
        try
        {
            problem = await response.Content.ReadFromJsonAsync<ProblemPayload>(ApiJson.Options, ct);
        }
        catch (JsonException)
        {
        }

        throw new ApiException(response.StatusCode, problem?.Title, problem?.Detail, problem?.Errors);
    }

    private sealed record ProblemPayload(string? Title, string? Detail, Dictionary<string, string[]>? Errors);
}

// Web/Api/ApiException.cs
public sealed class ApiException(
    HttpStatusCode statusCode,
    string? title,
    string? detail,
    IReadOnlyDictionary<string, string[]>? fieldErrors = null)
    : Exception(detail ?? title ?? "Ocurrió un error al comunicarse con el servicio.")
{
    public HttpStatusCode StatusCode { get; } = statusCode;
    public string? Title { get; } = title;
    public IReadOnlyDictionary<string, string[]>? FieldErrors { get; } = fieldErrors;
}
```

Este es el corazón del Gateway. La API responde con `ProblemDetails` según el mapeo de `ApiService/Exceptions/GlobalExceptionHandler.cs:18-37` —404, 400 con `ValidationProblemDetails`, 422—, y aquí ese cuerpo se convierte en **una sola** excepción del panel. El `catch (JsonException)` vacío es una degradación deliberada: un 500 sin cuerpo produce igualmente una `ApiException`, con mensaje genérico, en vez de un fallo de parseo incomprensible.

Gracias a eso, cada página tiene un solo tipo que capturar y un solo componente que pintarlo: `Components/Shared/ErrorAlert.razor`, que además sabe desplegar `FieldErrors` cuando el fallo fue de validación.

## 7.4 · Recorrido de una ejecución

Un usuario del panel crea un trigger con la clave `"pedido creado"` (con espacio: inválida).

<ol class="ddd-steps">
    <li>
        <strong><code>Components/Pages/Triggers/TriggersList.razor</code></strong> — el formulario llama a
        <code>TriggersApiClient.CreateAsync(new CreateTriggerRequest(...), ct)</code>. El
        <code>record</code> es el de <code>Web/Api/Triggers/TriggerModels.cs:11</code>, no el del servidor.
    </li>
    <li>
        <strong><code>TriggersApiClient.cs:30</code></strong> —
        <code>PostAsJsonAsync("/api/triggers", request, ApiJson.Options, ct)</code>.
        <code>ApiJson.Options</code> (<code>Web/Api/ApiJson.cs:7</code>) es
        <code>JsonSerializerDefaults.Web</code>: <em>camelCase</em>, el mismo que usa ASP.NET al recibir. Que
        sea una constante compartida y no una instancia por llamada es lo que evita que un método se desvíe.
    </li>
    <li>
        <strong>La red</strong> — el descubrimiento de servicios resuelve <code>apiservice</code> y la
        petición sale.
    </li>
    <li>
        <strong><code>ApiService</code></strong> — el endpoint construye el comando, el handler llama a
        <code>EventKey.Create</code>, el regex falla y sale un <code>DomainException</code>
        (<a href="/patrones/factory">ficha 1</a>). <code>GlobalExceptionHandler.cs:29-34</code> lo convierte
        en un <strong>422</strong> con título "Regla de negocio violada".
    </li>
    <li>
        <strong><code>ApiResponseExtensions.cs:12</code></strong> — de vuelta en el panel,
        <code>IsSuccessStatusCode</code> es falso.
    </li>
    <li>
        <strong><code>ApiResponseExtensions.cs:18</code></strong> — el cuerpo se lee como
        <code>ProblemPayload</code>, un <code>record</code> <strong>privado</strong> declarado en la línea 27.
        Ese tipo no sale nunca del fichero: es la forma del sistema ajeno, y muere aquí.
    </li>
    <li>
        <strong><code>ApiResponseExtensions.cs:24</code></strong> —
        <code>throw new ApiException(response.StatusCode, problem?.Title, problem?.Detail, problem?.Errors)</code>.
        A partir de este punto el panel ya no habla HTTP: habla su propio idioma de errores.
    </li>
    <li>
        <strong>La página</strong> captura <code>ApiException</code>, la guarda en un campo y la pasa a
        <code>&lt;ErrorAlert Exception="..." /&gt;</code>, que pinta el título y el detalle.
        <strong><code>CreateAsync</code> nunca llegó a deserializar nada</strong>: la línea 32 no se
        ejecutó.
    </li>
</ol>

<Callout kind="concepto" title="Dónde acaba el contrato de errores">

Fíjate en el trayecto completo de un error: `DomainException` (Domain) → `ProblemDetails` 422 (ApiService) → `ApiException` (Web) → `ErrorAlert` (UI). Cuatro representaciones del mismo hecho, cada una en el vocabulario de su capa, y **tres traductores**, cada uno en un único fichero. Ese es el patrón aplicado de punta a punta.

</Callout>

## 7.5 · Qué pasaría sin el patrón

Contraejemplo **hipotético**: la página hablando HTTP.

```csharp title="Hipotético — HttpClient dentro del componente"
// HIPOTÉTICO — el bloque de código de un componente .razor que inyecta HttpClient
private async Task CrearAsync()
{
    var response = await Http.PostAsJsonAsync(
        "https://localhost:7443/api/triggers",      // la URL, a mano, en cada página
        new { eventKey = _eventKey, description = _descripcion });

    if (!response.IsSuccessStatusCode)              // ...si alguien se acuerda de mirarlo
    {
        _error = await response.Content.ReadAsStringAsync();   // el JSON crudo, en pantalla
        return;
    }

    // sin ApiJson.Options: PascalCase por defecto, y el objeto llega vacío sin dar error
    var creado = await response.Content.ReadFromJsonAsync<CreatedResponse>();
}
```

Lo que se rompe:

- **La ruta y el contrato se copian por página.** Renombrar un endpoint obliga a buscar cadenas de texto por todo el proyecto en vez de cambiar un método.
- **El manejo de errores se vuelve incoherente.** Cada componente decide si mira el código de estado, y el que no lo mire deserializará un cuerpo de error como si fuera un resultado —con `ReadFromJsonAsync` devolviendo `null` y un `NullReferenceException` tres líneas más tarde.
- **Las opciones de JSON se dispersan.** Basta con que un componente use el `JsonSerializerOptions` por defecto (PascalCase) para que la deserialización devuelva objetos vacíos sin error.

**Qué se paga:** duplicación de modelos. `TriggerSummaryDto` existe dos veces —`Application/Triggers/Queries/ListTriggers/TriggerSummaryDto.cs` y `Web/Api/Triggers/TriggerModels.cs:3`— y nada garantiza que sigan iguales. La alternativa sería un proyecto `Contracts` compartido, que elimina la duplicación a cambio de acoplar el despliegue del panel al de la API: un cambio en el contrato obliga a recompilar y desplegar los dos a la vez. Aquí se eligió la duplicación, y para un panel interno que se despliega junto a su API es una elección defendible — pero es una elección, y tiene una factura. El ejercicio la muestra.

## 7.7 · Señales de alarma

- **Un `HttpResponseMessage` devuelto por un método público del cliente.** Sería el fin del patrón: el protocolo se escaparía a las páginas.
- **Una página que inyecta `HttpClient`.** Fácil de detectar en revisión y fácil de justificar mal ("es solo una llamadita").
- **Deriva entre las dos copias de los modelos.** No hay compilador que la detecte. El único punto donde el proyecto se protege es un comentario: `Web/Api/Shared.cs:8-9`. Ver el ejercicio.
- **El `!` tras `ReadFromJsonAsync`.** Aparece en todos los métodos de lectura (`TriggersApiClient.cs:18`, por ejemplo). Es correcto en la práctica —tras `EnsureSuccessAsync` hay cuerpo—, pero convierte un `null` inesperado (un 204 donde se esperaba 200) en un `NullReferenceException` lejos del origen.
- **Reintentos y *circuit breakers* añadidos por página.** Si algún día hacen falta, el sitio es el registro de `Program.cs`, no el método del cliente ni el componente.

<Callout kind="ejercicio" title="Ejercicio">

`PagedResult<T>` está escrito **dos veces**: en `Application/Common/PagedResult.cs` y en `Web/Api/Shared.cs`.

**(a)** Compara ambas. Hay una propiedad calculada cuyo cuerpo **ya ha divergido**. Encuéntrala y cita las dos líneas.

**(b)** ¿Con qué valores de entrada las dos copias devuelven cosas distintas? ¿Cuál es la correcta para lo que hace el panel?

**(c)** En el mismo `Shared.cs` hay otra duplicación con un comentario que advierte de un riesgo. Descríbelo y explica qué fallo concreto —y silencioso— aparecería si alguien añadiera un canal al dominio y olvidara el espejo.

**Verificación:** (b) debe nombrar un valor concreto de `TotalCount`, y (c) debe explicar por qué el fallo sería silencioso y no una excepción.

</Callout>

    <summary><strong>Ver solución</strong></summary>
    <p><strong>(a)</strong> Es <code>TotalPages</code>:</p>
    <Code code={"// Application/Common/PagedResult.cs:9  (servidor)\npublic int TotalPages => (int)Math.Ceiling(TotalCount / (double)PageSize);\n\n// Web/Api/Shared.cs:5  (panel)\npublic int TotalPages => Math.Max(1, (int)Math.Ceiling(TotalCount / (double)PageSize));"} lang="csharp" title="Las dos copias, una al lado de la otra" />
    <p>
        La del panel envuelve el cálculo en <code>Math.Max(1, ...)</code>. La del servidor, no.
    </p>
    <p>
        <strong>(b)</strong> Difieren cuando <code>TotalCount == 0</code>: el servidor devuelve
        <strong>0</strong> y el panel <strong>1</strong>. (Con cualquier <code>TotalCount &gt; 0</code> el
        <code>Math.Max</code> es inocuo, porque el techo de un número positivo ya es al menos 1.)
    </p>
    <p>
        La correcta para el panel es la suya: <code>Components/Shared/Pager.razor</code> muestra "página X de
        Y" y necesita que Y sea al menos 1, porque una lista vacía sigue estando en la página 1. Un
        <code>0</code> produciría "página 1 de 0". Para la API, en cambio, <code>0</code> es más honesto: no
        hay ninguna página de resultados.
    </p>
    <p>
        Es decir: <strong>la divergencia no es un fallo, es una adaptación legítima al consumidor</strong>.
        Y ese es justamente el argumento a favor de duplicar el modelo en vez de compartirlo — cada lado
        puede tener la forma que le sirve. Lo que hay que tener claro es que la deriva es posible y que
        nadie avisará de ella: aquí resultó benigna, pero el mecanismo que la permitió es el mismo que
        permitiría una maligna.
    </p>
    <p>
        <strong>(c)</strong> La otra duplicación es el <code>enum NotificationChannel</code>
        (<code>Web/Api/Shared.cs:10-16</code>), espejo del de
        <code>Domain/Shared/NotificationChannel.cs</code>. El comentario de las líneas 8-9 lo dice: los
        valores numéricos deben coincidir <em>porque el canal viaja como número</em> en el cuerpo de las
        peticiones (no hay <code>JsonStringEnumConverter</code> registrado, así que System.Text.Json
        serializa el <code>enum</code> como entero).
    </p>
    <p>
        El fallo si el espejo se desincroniza sería <strong>silencioso porque los dos lados serían
        internamente coherentes</strong>. Imagina que el dominio inserta <code>Telegram = 3</code> y
        renumera <code>Push = 5</code>, y el panel no se actualiza: al añadir una configuración de Push
        desde la interfaz, <code>AddConfigurationRequest</code>
        (<code>Web/Api/Triggers/TriggerModels.cs:17</code>) viajaría con <code>"channel": 3</code>, y el
        servidor lo deserializaría como un <code>NotificationChannel</code> perfectamente válido — Telegram.
        No hay excepción, no hay 400: <code>Enum.IsDefined</code> en
        <code>NotificationConfiguration.cs:21</code> lo aprobaría, porque el valor <em>existe</em>. El error
        solo se descubriría al ver que las notificaciones salen por el canal equivocado.
    </p>
    <p>
        Dos formas de cerrar el hueco sin renunciar a la duplicación: registrar
        <code>JsonStringEnumConverter</code> en los dos extremos, de modo que el canal viaje como
        <code>"Push"</code> y un nombre desconocido produzca un 400 ruidoso; o un test del panel que compare
        los nombres y valores de las dos enumeraciones por reflexión. La segunda cuesta diez líneas y
        convierte un fallo de producción en uno de compilación continua.
    </p>
</details>
