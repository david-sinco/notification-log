<Callout kind="concepto" title="Ficha rápida">

- **Tipo:** idiom / patrón de comportamiento. No está en el GoF; viene del mundo funcional (`Either`, `Result`).
- **Origen:** deliberado, y limitado a un sitio muy concreto: el borde de salida hacia proveedores externos.
- **Dónde:** `NotificationSendResult`, devuelto por las cuatro interfaces de envío y consumido en `NotificationDispatchService`.

</Callout>

## 4.1 · El problema

Enviar una notificación falla de dos maneras que *parecen* la misma y no lo son:

- **El proveedor contestó y dijo que no.** El servidor SMTP rechaza la dirección, el gateway de SMS devuelve un 422 porque el número no existe. Esto no es un error del sistema: es un resultado de negocio, tan esperable como el éxito, y hay que *registrarlo* — con su motivo — y seguir con el siguiente canal.
- **El proveedor no contestó.** Conexión rechazada, DNS caído, timeout. Aquí no hay resultado: hay una avería.

Si las dos se modelan como excepción, el llamante tiene que hacer arqueología sobre tipos de excepción ajenos para distinguirlas, y el camino "esperable" del código pasa por un `catch`. Si las dos se modelan como valor, hay que envolver medio mundo en `try/catch` dentro de cada sender solo para convertir cualquier avería en un objeto — y se pierde el *stack trace*, que para una avería es justo lo que hace falta.

## 4.2 · La idea del patrón

El fallo *esperado* deja de ser una excepción y pasa a ser parte del tipo de retorno. La operación devuelve un objeto que dice si salió bien y, si no, por qué. El llamante no puede ignorarlo: para llegar al dato tiene que mirar el resultado.

La clave está en la palabra "esperado". El patrón no sustituye a las excepciones, reparte el trabajo con ellas: **valor para lo que forma parte del dominio del problema, excepción para lo que no debería estar pasando**. Aplicar Result a todo termina en un código lleno de comprobaciones y de fallos propagados a mano; no aplicarlo nunca convierte los casos normales en excepciones.

## 4.3 · Cómo se ve aquí

```csharp title="Application/Notifications/Services/Sending/NotificationSendResult.cs:3-8 (completo)"
public sealed record NotificationSendResult(bool Succeeded, string? ProviderMessageId, string? Error)
{
    public static NotificationSendResult Success(string? providerMessageId) => new(true, providerMessageId, null);

    public static NotificationSendResult Failure(string error) => new(false, null, error);
}
```

Ocho líneas. Las piezas:

- **`Succeeded`** es el discriminante, y los otros dos campos son mutuamente excluyentes por convención (no por tipo — ver las señales de alarma).
- **`Success` y `Failure`** son fábricas con nombre, el mismo patrón de [la ficha 1](/patrones/factory): hacen imposible construir un fracaso sin motivo o un éxito con error, sin escribir ni una validación.
- **Vive en `Application`**, no en `Domain`, porque no es un concepto de negocio: es el contrato de un puerto de salida.

La regla se ve entera en el sender de correo, con su justificación escrita al lado:

```csharp title="Infrastructure/Notifications/Sending/Email/SmtpEmailNotificationSender.cs:36-47"
        try
        {
            await client.SendMailAsync(mail, ct);
            return NotificationSendResult.Success(null);
        }
        catch (SmtpException ex)
        {
            // Rechazo del servidor SMTP (destinatario inválido, etc.) — es un resultado de negocio,
            // no un error inesperado; fallas de transporte (conexión caída) sí se dejan propagar
            // para que NotificationDispatchService las registre como falla con su propio try/catch.
            return NotificationSendResult.Failure(ex.Message);
        }
```

`catch (SmtpException)`, no `catch (Exception)`. Ese tipo concreto *es* la regla: un `SmtpException` significa que un servidor contestó y rechazó el mensaje. Cualquier otra cosa —`SocketException`, un timeout— no se captura y sube.

El sender de SMS aplica el mismo criterio sin necesitar un `catch`:

```csharp title="Infrastructure/Notifications/Sending/Sms/HttpSmsNotificationSender.cs:27-41"
        var response = await _client.PostAsJsonAsync(
            _options.Path,
            new SendSmsRequest(_options.From, destination, message.Body),
            JsonOptions,
            ct);

        if (!response.IsSuccessStatusCode)
        {
            var errorBody = await response.Content.ReadAsStringAsync(ct);
            return NotificationSendResult.Failure($"HTTP {(int)response.StatusCode}: {errorBody}");
        }

        var body = await response.Content.ReadAsStringAsync(ct);
        return NotificationSendResult.Success(TryReadMessageId(body));
```

Un código HTTP fuera de 2xx es la versión REST de "el proveedor contestó que no" → `Failure`. Un `HttpRequestException` —que `PostAsJsonAsync` lanza cuando no hay a quién conectarse— no se captura → sube. La correspondencia con el sender de SMTP es exacta.

### Y el que decide, decide una sola vez

```csharp title="Application/…/Dispatch/NotificationDispatchService.cs:127-161 (extracto)"
        try
        {
            var result = await SendAsync(configuration.Channel, destination, message, ct);

            if (result.Succeeded)
            {
                await _recordSuccess.HandleAsync(
                    new RecordNotificationSuccessCommand(
                        /* ... */ result.ProviderMessageId, DateTime.UtcNow, businessEvent.Data),
                    ct);
            }
            else
            {
                await _recordFailure.HandleAsync(
                    new RecordNotificationFailureCommand(
                        /* ... */ result.Error ?? "Error desconocido", DateTime.UtcNow, businessEvent.Data),
                    ct);
            }
        }
        catch (Exception ex)
        {
            _log.LogError(ex,
                "Fallo al enviar la notificación del evento {EventKey} al destinatario {RecipientId} por {Channel}",
                eventKey, recipient.Id, configuration.Channel);

            await _recordFailure.HandleAsync(
                new RecordNotificationFailureCommand(
                    /* ... */ ex.Message, DateTime.UtcNow, businessEvent.Data),
                ct);
        }
```

Aquí está lo que hace que el diseño funcione: **los dos caminos terminan en el mismo sitio**. El `else` del resultado y el `catch` de la excepción construyen el mismo `RecordNotificationFailureCommand`. La diferencia no está en lo que se persiste, sino en *qué se considera digno de un `LogError`*: la avería sí (línea 152), el rechazo no.

Un evento `pedido.creado` para un destinatario cuyo correo el servidor SMTP rechaza (`550 Mailbox unavailable`).

<Callout kind="honesto" title="Compara con el camino de la avería">

Si en el paso 2 el servidor SMTP estuviera apagado, el `catch (SmtpException)` no atraparía el `SocketException`, y este subiría hasta el `catch (Exception ex)` de `NotificationDispatchService.cs:150`. El resultado *persistido* sería idéntico: una notificación fallida con el mensaje de la excepción. Lo único que cambia es que además se emite un `LogError` con el stack trace.

Esa simetría es intencionada y es el gran acierto del diseño: **ninguna notificación se pierde en silencio**, venga el fallo por donde venga. El patrón Result no está aquí para evitar excepciones, sino para separar lo que hay que investigar de lo que solo hay que registrar.

</Callout>

## 4.5 · Qué pasaría sin el patrón

Contraejemplo **hipotético**: todo por excepciones.

```csharp title="Hipotético — el rechazo como excepción"
// HIPOTÉTICO — así NO está el código
public interface IEmailNotificationSender
{
    // lanza SmtpException si el servidor rechaza, o lo que sea si no hay conexión
    Task<string?> SendAsync(string destination, RenderedMessage message, CancellationToken ct);
}

// y en el servicio de dispatch, un único catch que ya no distingue nada:
try
{
    var providerMessageId = await _emailSender.SendAsync(destination, message, ct);
    await _recordSuccess.HandleAsync(/* ... */);
}
catch (Exception ex)   // ¿buzón lleno o cortafuegos? Imposible saberlo aquí.
{
    await _recordFailure.HandleAsync(/* ... */);
}
```

Lo que se rompe:

- **El camino normal pasa por un `catch`.** Rechazar un correo por dirección inválida es un desenlace previsto y frecuente; tratarlo como excepción confunde a quien lee y a quien monitoriza.
- **El llamante no puede distinguir.** Con un solo `catch (Exception)`, un buzón lleno y un cortafuegos mal configurado producen exactamente la misma traza. Distinguirlos exigiría capturar tipos de excepción de cada librería de proveedor *en la capa de aplicación*, que es justo lo que las interfaces de envío existen para evitar.
- **Se pierde el `ProviderMessageId`.** El camino de éxito también necesita devolver algo: hoy el identificador que da el proveedor viaja en el mismo objeto (`NotificationSendResult.cs:3`) y acaba en la columna homónima de la tabla.

**Qué se paga:** el compilador no obliga a mirar `Succeeded`. Un `await sender.SendAsync(...)` que descarte el resultado compila sin una advertencia, y el fallo desaparece. Un `Result` de verdad —un tipo suma con dos casos— lo impediría; este es un `record` de tres campos donde `Succeeded == true` y `Error != null` es representable aunque las fábricas no lo construyan.

## 4.7 · Señales de alarma

- **Un resultado que se descarta.** Es el fallo característico del patrón. Busca en revisión cualquier `SendAsync` cuyo retorno no se asigne.
- **`catch (Exception)` dentro de un sender.** Convierte una avería en un resultado de negocio y hace desaparecer el stack trace. El `catch` tipado de `SmtpEmailNotificationSender.cs:41` es la forma correcta.
- **Un `Error` que solo es texto.** Hoy `NotificationSendResult` no distingue "número inválido" (nunca funcionará) de "límite de tasa superado" (funcionará en un minuto). El día que se quiera reintentar, hará falta un código de error o un `bool IsTransient`; parsear el mensaje sería el antipatrón clásico.
- **Estados imposibles representables.** `new NotificationSendResult(true, null, "algo falló")` compila. Las fábricas lo evitan por convención, no por tipo; si el `record` deja de ser el único punto de construcción, la garantía se cae.
- **Result colonizando la capa de aplicación.** Si un handler empieza a devolver `Result<Guid>`, el contrato de errores de la API —el mapeo de `GlobalExceptionHandler`— deja de aplicarse y cada endpoint tiene que traducir a mano. Mezclar los dos estilos en la misma capa es peor que elegir cualquiera de ellos.
