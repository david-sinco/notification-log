## Dos procesos, no un monolito con vistas

`NotificationLog.ApiService` y `NotificationLog.Web` son proyectos ejecutables independientes. El primero solo expone HTTP + JSON; el segundo es un Blazor Server que renderiza el panel de administración y, para cualquier dato, llama al primero por HTTP — nunca referencia sus proyectos de `Application` o `Infrastructure` directamente. Es la misma regla de dependencia de las capas internas, aplicada a nivel de despliegue: el navegador nunca toca la base de datos ni la cola, solo la API.

## API: endpoints agrupados, ProblemDetails como contrato de error

Cada grupo de endpoints (`TriggerEndpoints`, `TemplateEndpoints`, `RecipientEndpoints`, `NotificationEndpoints`) es una clase estática con un método de extensión (`MapTriggers`, etc.) que registra su grupo bajo `/api/<recurso>` y documenta cada ruta con `WithSummary` y `Produces` para que Scalar (la UI de OpenAPI en desarrollo) las muestre bien tipadas.

```csharp title="ApiService/Endpoints/TriggerEndpoints.cs (extracto)"
public static class TriggerEndpoints
{
    public static IEndpointRouteBuilder MapTriggers(this IEndpointRouteBuilder app)
    {
        var group = app.MapGroup("/api/triggers").WithTags("Triggers");

        group.MapPost("/", CreateAsync)
            .WithName("CreateTrigger")
            .Produces<CreatedTriggerResponse>(StatusCodes.Status201Created)
            .ProducesProblem(StatusCodes.Status422UnprocessableEntity);
        // ... 8 rutas más: GET por id, listado paginado, status, descripción, configuraciones
        return app;
    }

    private static async Task<IResult> CreateAsync(
        CreateTriggerRequest body, CreateTriggerHandler handler, CancellationToken ct)
    {
        var id = await handler.HandleAsync(new CreateTriggerCommand(body.EventKey, body.Description), ct);
        return Results.CreatedAtRoute("GetTriggerById", new { id }, new CreatedTriggerResponse(id));
    }
}
```

Ningún endpoint contiene lógica de negocio: recibe el request, arma el comando, llama al handler inyectado directo (sin mediador — ver [decisiones](/arquitectura/decisiones)) y traduce el resultado a un código HTTP. Las excepciones de dominio y de aplicación nunca llegan crudas al cliente: `GlobalExceptionHandler` las traduce a `ProblemDetails` con el código correcto.

```csharp title="ApiService/Exceptions/GlobalExceptionHandler.cs (extracto)"
var problem = exception switch
{
    NotFoundException e => new ProblemDetails { Status = 404, Title = "Recurso no encontrado", Detail = e.Message },
    AppValidationException e => BuildValidationProblem(e),          // 400 + errores por campo
    DomainException e => new ProblemDetails
    {
        Status = StatusCodes.Status422UnprocessableEntity,
        Title = "Regla de negocio violada",   // <- el dominio nunca supo que esto sería un 422
        Detail = e.Message
    },
    _ => null   // deja que el pipeline devuelva 500
};
```

## Web: Blazor Server con clientes HTTP tipados

`NotificationLog.Web` no tiene su propio modelo de datos ni acceso a base de datos. Por cada recurso hay un `ApiClient` (`TriggersApiClient`, `TemplatesApiClient`…) inyectado como `HttpClient` tipado, cuya URL base usa el esquema `https+http://apiservice` — el descubrimiento de servicios de .NET Aspire resuelve ese nombre lógico a la URL real del contenedor/proceso en cada entorno, sin hardcodear puertos.

```csharp title="Web/Program.cs (extracto)"
builder.Services.AddRazorComponents()
    .AddInteractiveServerComponents();

// La URL usa "https+http://" para preferir HTTPS cuando esté disponible; la resuelve el
// descubrimiento de servicios de Aspire.
builder.Services.AddHttpClient<TriggersApiClient>(client => client.BaseAddress = new("https+http://apiservice"));
builder.Services.AddHttpClient<TemplatesApiClient>(client => client.BaseAddress = new("https+http://apiservice"));
builder.Services.AddHttpClient<RecipientsApiClient>(client => client.BaseAddress = new("https+http://apiservice"));
builder.Services.AddHttpClient<NotificationsApiClient>(client => client.BaseAddress = new("https+http://apiservice"));

app.MapRazorComponents<App>()
    .AddInteractiveServerRenderMode();
```

```csharp title="Web/Api/Triggers/TriggersApiClient.cs (extracto)"
public sealed class TriggersApiClient(HttpClient http)
{
    public async Task<PagedResult<TriggerSummaryDto>> ListAsync(
        string? search, bool? isEnabled, int page, int pageSize, CancellationToken ct)
    {
        var query = QueryString.Build(("search", search), ("isEnabled", isEnabled?.ToString()),
            ("page", page.ToString()), ("pageSize", pageSize.ToString()));

        var response = await http.GetAsync($"/api/triggers{query}", ct);
        await response.EnsureSuccessAsync(ct);   // traduce error HTTP -> ApiException
        return (await response.Content.ReadFromJsonAsync<PagedResult<TriggerSummaryDto>>(ApiJson.Options, ct))!;
    }
}
```

<Callout kind="concepto" title="Por qué esto no es 'llamar directo a Application'">

Sería más rápido que `NotificationLog.Web` referenciara los proyectos de `Application`/`Infrastructure` y evitara el salto HTTP. La decisión de mantenerlo como cliente HTTP separado paga dos cosas: permite escalar o desplegar la API independientemente del panel, y fuerza a que el único contrato entre ambos sea HTTP + JSON — el mismo contrato que usaría cualquier otro consumidor futuro (una app móvil, un script de soporte).

</Callout>

## Interactive Server, no WebAssembly

El modo de render es `AddInteractiveServerComponents` / `AddInteractiveServerRenderMode`: la UI corre en el servidor y se sincroniza con el navegador por una conexión persistente (SignalR), no se compila a WebAssembly. Para un panel interno de administración, evita enviar el runtime de .NET al navegador a cambio de mantener una conexión con estado por sesión — una decisión razonable de tamaño de proyecto, no la única opción posible.
