## Una carpeta por feature, un caso de uso por clase

No hay un `TriggerService` con quince métodos. Cada operación —crear un trigger, agregar una configuración, deshabilitarla, cambiar su plantilla— vive en su propia carpeta con tres archivos: comando, handler y (cuando aplica) validador. `Triggers/Commands/` tiene hoy nueve carpetas así; `Templates/`, `Recipients/` y `Notifications/` siguen el mismo patrón.

```text title="Application/Triggers — estructura real de carpetas"
Application/Triggers/
├── Commands/
│   ├── AddConfiguration/
│   ├── ChangeConfigurationTemplate/
│   ├── CreateTrigger/
│   │   ├── CreateTriggerCommand.cs
│   │   ├── CreateTriggerHandler.cs
│   │   └── CreateTriggerValidator.cs
│   ├── DisableConfiguration/
│   ├── EnableConfiguration/
│   ├── SetTriggerStatus/
│   └── UpdateTriggerDescription/
├── Queries/
│   ├── GetTriggerById/
│   └── ListTriggers/
└── Dtos/
```

## Los puertos que Application define

La capa de aplicación no implementa infraestructura, pero sí **declara los contratos** que necesita de ella. Son interfaces con vocabulario de negocio, no de tecnología — ninguna menciona SQL, HTTP ni un proveedor concreto:

- `IUnitOfWork` (`Abstractions/`): un único método, `SaveChangesAsync`. No expone `DbContext` ni transacciones explícitas — Infrastructure decide cómo cumplirlo.
- `INotificationTriggerRepository`, `INotificationTemplateRepository`, `IRecipientRepository`, `INotificationRepository`: uno por agregado, cada uno con métodos de negocio (`GetByEventKeyAsync`, no `GetAll`).
- `ITemplateRenderer` (`Notifications/Services/Rendering/`): "dame un `RenderedMessage` a partir de una plantilla y datos". No sabe si detrás hay Scriban, Handlebars o interpolación manual.
- `IEmailNotificationSender`, `ISmsNotificationSender`, `IPushNotificationSender`, `IWhatsAppNotificationSender` (`Notifications/Services/Sending/`): un remitente por canal, mismo contrato (`SendAsync` → `NotificationSendResult`).

```csharp title="Application/Abstractions/IUnitOfWork.cs (completo)"
public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(CancellationToken ct);
}
// Implementado por NotificationDbContext (Infrastructure), que ya es un DbContext: no hace
// falta un wrapper adicional — ver la página de Infraestructura.
```

<Callout kind="honesto" title="Los cuatro puertos de envío ya tienen adaptador — uno de ellos, a propósito, siempre falla">

`IEmailNotificationSender`, `ISmsNotificationSender` e `IPushNotificationSender` tienen implementación real en `Infrastructure/Notifications/Sending`, y `ITemplateRenderer` también — `ScribanTemplateRenderer`, registrado como singleton. `IWhatsAppNotificationSender` también está registrado, pero con un stub que siempre lanza `NotSupportedException`: no hay proveedor de WhatsApp elegido todavía, y un envío que "funcionara" en silencio sería peor que uno que queda registrado como notificación fallida con el motivo exacto. Verás el detalle de cada adaptador en la [página de Infraestructura](/arquitectura/infraestructura).

</Callout>

## Un handler típico: 5-15 líneas, cero condicionales de negocio

`CreateTriggerHandler` es el ejemplo canónico: valida la forma del comando, construye el value object, comprueba una regla *entre* agregados (unicidad, que requiere consultar el repositorio) y delega todo lo demás al agregado. El reparto es siempre el mismo, y se puede leer directamente en el orden de las líneas: forma del mensaje → FluentValidation; regla dentro de un agregado → el propio agregado; regla entre agregados o que necesita consultar la base → el handler.

```csharp title="Application/Triggers/Commands/CreateTrigger/CreateTriggerHandler.cs"
public sealed class CreateTriggerHandler
{
    public async Task<Guid> HandleAsync(CreateTriggerCommand cmd, CancellationToken ct)
    {
        await _validator.ValidateAndThrowAppAsync(cmd, ct);           // forma del mensaje

        var eventKey = EventKey.Create(cmd.EventKey);                 // regla del value object

        if (await _triggers.ExistsAsync(eventKey, ct))                // regla entre agregados (unicidad)
            throw new AppValidationException($"Ya existe un trigger para '{eventKey}'.");

        var trigger = NotificationTrigger.Create(eventKey, cmd.Description);  // regla del agregado

        await _triggers.AddAsync(trigger, ct);
        await _uow.SaveChangesAsync(ct);

        return trigger.Id;
    }
}
```

## FluentValidation reutiliza las constantes del dominio

El validador no inventa su propio límite de longitud: importa `EventKey.MaxLength` y `NotificationTrigger.DescriptionMaxLength` directamente del dominio. Si el límite cambia, el validador cambia solo, sin tocar un número mágico duplicado.

```csharp title="Application/Triggers/Commands/CreateTrigger/CreateTriggerValidator.cs (completo)"
internal sealed class CreateTriggerValidator : AbstractValidator<CreateTriggerCommand>
{
    public CreateTriggerValidator()
    {
        RuleFor(x => x.Description)
            .NotEmpty()
            .MaximumLength(NotificationTrigger.DescriptionMaxLength);   // <- constante del dominio

        RuleFor(x => x.EventKey)
            .NotEmpty()
            .MaximumLength(EventKey.MaxLength);                        // <- constante del dominio
    }
}
```

## La pieza que orquesta el negocio de punta a punta

`NotificationDispatchService` es la clase más importante de esta capa y la única que no es un handler de comando: recibe un `BusinessEvent` ya traducido, busca el trigger por `EventKey`, recorre sus configuraciones activas, renderiza la plantilla por destinatario y llama al remitente del canal correspondiente — registrando éxito o fallo como una `Notification` en cada paso. Está registrada en el contenedor de dependencias como cualquier otro handler; no necesita ningún cableado especial.

```csharp title="Application/Notifications/Services/Dispatch/NotificationDispatchService.cs (extracto)"
public async Task DispatchAsync(BusinessEvent businessEvent, CancellationToken ct)
{
    var trigger = await _triggers.GetByEventKeyAsync(EventKey.Create(businessEvent.EventKey), ct);
    if (trigger is null || !trigger.IsEnabled) { /* log y salir */ return; }

    var recipient = await _recipients.GetByIdAsync(businessEvent.RecipientId, ct);
    if (recipient is null) { /* log y salir */ return; }

    foreach (var configuration in trigger.ResolveActiveConfigurations())
        await DispatchConfigurationAsync(businessEvent, trigger.EventKey.Value, configuration, recipient, ct);
}

private Task<NotificationSendResult> SendAsync(NotificationChannel channel, string destination,
    RenderedMessage message, CancellationToken ct) => channel switch
{
    NotificationChannel.Email => _emailSender.SendAsync(destination, message, ct),
    NotificationChannel.Sms => _smsSender.SendAsync(destination, message, ct),
    NotificationChannel.Push => _pushSender.SendAsync(destination, message, ct),
    NotificationChannel.WhatsApp => _whatsAppSender.SendAsync(destination, message, ct),
    _ => throw new InvalidOperationException($"El canal '{channel}' no tiene un remitente registrado.")
};
```

<Callout kind="honesto" title="La lógica está completa. Lo que falta es quién la dispare de verdad">

`NotificationDispatchService` está registrada, sus cuatro puertos de envío tienen adaptador y el consumer de infraestructura que la invoca (`NotificationDispatchHandler`, escuchando la cola `notification-dispatch`) también existe. Lo único que falta en todo este flujo es un **productor**: ningún sistema de negocio publica hoy un `BusinessEvent` real hacia esa cola. La única forma de ejercitar el flujo completo hoy es publicar un mensaje a mano desde la UI de administración de RabbitMQ. Verás el resto de este flujo, y ese vacío exacto, en [la página funcional correspondiente](/proyecto/flujo-notificacion).

</Callout>
