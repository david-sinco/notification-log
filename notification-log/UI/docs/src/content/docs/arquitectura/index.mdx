Esta guía tiene dos mitades que se necesitan. La primera enseña arquitectura de software —qué decisiones son arquitectura, cómo se eligen, qué duele al distribuir, cómo se evita que todo se degrade con el tiempo— y la segunda recorre las capas de este proyecto con archivos reales: `Domain`, `Application`, `Infrastructure` y la pareja `API`/`Web`. Ningún concepto se explica con la tienda online imaginaria de siempre: se explica señalando un archivo de este repositorio que puedes abrir y comprobar.

Y donde este sistema no hace lo que el concepto recomienda —no hay ADRs, no hay outbox, no hay autenticación, no hay tests de arquitectura— la guía lo dice de frente y explica qué costaría arreglarlo. Un sistema real nunca se parece a la foto del libro; aprender a leer esa diferencia es buena parte del trabajo.

Hay una pregunta que atraviesa las once páginas y que conviene repetir en cada decisión que discutas con tu equipo: **"¿qué atributo de calidad estamos comprando, y cuál estamos pagando?"**. No existen arquitecturas buenas; existen compromisos adecuados a un contexto. Si una propuesta solo enumera ventajas, el análisis todavía no está terminado.

## Bloque B · Este sistema, capa por capa

La regla que sostiene todo el proyecto es una sola: **las dependencias apuntan hacia adentro**. `Domain` no conoce a nadie. `Application` solo conoce a `Domain`. `Infrastructure` conoce a los dos anteriores e implementa sus interfaces. `API` y `Web` son los bordes que hablan con el mundo exterior — HTTP, un navegador — y traducen hacia y desde ese núcleo. Es la misma regla que ya viste aplicada al modelo de dominio en [el módulo 11 del tutorial de DDD](/ddd/arquitectura); aquí la recorremos capa por capa, con más detalle de infraestructura real: Entity Framework, RabbitMQ, Aspire.

## Si vas a impartir esto

Tres errores hunden cualquier formación de arquitectura, y los tres son fáciles de cometer:

<ol class="ddd-steps">
    <li>
        <strong>Enseñar un catálogo de estilos.</strong> El equipo memoriza "microservicios frente a
        monolito" y sale creyendo que arquitectura es elegir una caja. Arquitectura es elegir qué se
        sacrifica.
    </li>
    <li>
        <strong>Presentarla como algo del arquitecto.</strong> Si el mensaje es "esto lo decide otro", nadie
        aplica nada. El mensaje correcto es que todos toman decisiones arquitectónicas cada semana; la
        diferencia está en si son conscientes y quedan registradas.
    </li>
    <li>
        <strong>Omitir el coste.</strong> Cada patrón de esta guía tiene un precio en complejidad operativa.
        Preséntalo siempre junto al beneficio, o acabarás con un equipo con síndrome de arquitectura de CV.
    </li>
</ol>

El formato que funciona en cada bloque es el mismo: **concepto (10 min) → aplicarlo a nuestro sistema (10 min) → discusión del trade-off (10 min)**. La segunda parte es la que hace que se recuerde, y es la razón de que esta guía use este repositorio como material de práctica en lugar de un ejemplo inventado.

<Callout kind="honesto" title="Cómo se relaciona con el tutorial de DDD">

El [tutorial de DDD](/ddd) cubre el modelado táctico —agregados, value objects, invariantes— y tiene su propio módulo de arquitectura centrado en Clean Architecture y CQRS. Esta guía trabaja el nivel de encima: qué decisiones son arquitectura, cómo se eligen entre alternativas, qué pasa cuando el sistema se distribuye y cómo se evita que se degrade. Se solapan poco y a propósito; donde lo hacen, cada página enlaza a la otra en vez de repetirla.

</Callout>
