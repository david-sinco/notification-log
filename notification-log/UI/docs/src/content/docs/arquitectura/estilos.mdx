## 3.1 · Monolito

Todo el sistema en un único artefacto desplegable. Sus ventajas se olvidan por costumbre, así que conviene enumerarlas: transacciones ACID sencillas, refactor global con el IDE, depuración de un flujo completo con un solo *step into*, un solo pipeline, un solo sitio donde mirar los logs.

Este sistema las usa todas. `CreateTriggerHandler` comprueba unicidad y guarda en la misma transacción implícita de `SaveChangesAsync`: no hay compensación, ni saga, ni ventana de inconsistencia. Si `apiservice` fueran tres servicios, esa comprobación de unicidad sería un problema distribuido con respuesta mucho más larga.

```csharp title="Lo que un monolito te regala y un sistema distribuido te cobra"
// CreateTriggerHandler: unicidad y escritura en la misma transaccion implicita.
if (await _triggers.ExistsAsync(eventKey, ct))
    throw new AppValidationException($"Ya existe un trigger para '{eventKey}'.");

var trigger = NotificationTrigger.Create(eventKey, cmd.Description);

await _triggers.AddAsync(trigger, ct);
await _uow.SaveChangesAsync(ct);      // <- ACID. Sin saga, sin compensacion, sin ventana.

// Ademas, la base lo respalda con un indice unico (NotificationTriggerConfiguration):
//   builder.HasIndex(t => t.EventKey).IsUnique()
// La comprobacion en codigo da un buen mensaje de error; el indice da la garantia real
// cuando dos peticiones entran a la vez. En un sistema distribuido, esa segunda red de
// seguridad no existiria: haria falta una saga o una clave de idempotencia.
```

El monolito solo es un problema cuando es un *big ball of mud* — y eso es un fallo de modularidad, no de despliegue. La respuesta correcta a "nuestro monolito es un desastre" casi nunca es "repartámoslo en servicios": es "pongámosle límites y tests que los defiendan".

## 3.2 · Microservicios

Servicios pequeños, desplegables de forma independiente, con datos propios y alineados a capacidades de negocio. El beneficio central **no es técnico, es organizativo**: despliegue y evolución independientes por equipo. Si no tienes varios equipos pisándose en el mismo release, probablemente no los necesitas.

Y el coste, sin edulcorar:

- Consistencia eventual donde antes había una transacción.
- Depuración distribuida: sin trazas correlacionadas, un fallo es indepurable.
- Latencia de red en cada salto y modos de fallo parciales nuevos.
- Versionado de contratos con consumidores que no controlas.
- Entornos locales complicados de levantar.
- CI/CD y observabilidad dejan de ser opcionales.
- El coste en personas de operarlo, que es el que nadie presupuesta.

**Regla práctica:** el tamaño correcto de un servicio lo marca el límite de negocio (*bounded context*), no el número de líneas.

<Callout kind="honesto" title="Este sistema no es microservicios, aunque los nombres lo sugieran">

Hay dos procesos desplegables — `apiservice` y `webfrontend` — y la separación no responde a límites de negocio, sino a la frontera entre UI y API. Todo el negocio vive en uno solo. Los nombres (`NotificationService.Domain`, la carpeta `Services/Notification/`, el proyecto `Contracts` con sus `.proto`) delatan que el diseño está *preparado* para que aparezcan más servicios alrededor, y eso está bien: preparar el vocabulario y los contratos es barato, partir el despliegue antes de necesitarlo no.

Dicho eso, el proyecto ya paga **parte** del coste distribuido sin cobrar el beneficio: un salto HTTP entre Web y API, una cola de mensajería con entrega al menos una vez y dos formatos de serialización. Es una elección defendible —la mensajería es el punto de integración real con otros sistemas— pero hay que verla como lo que es: un precio ya pagado.

</Callout>

## 3.3 · Arquitectura orientada a eventos

Los componentes se comunican publicando y consumiendo eventos a través de un broker, sin conocerse entre sí. Hay dos modelos, y no son intercambiables:

| Modelo | Cómo funciona | Coste |
| --- | --- | --- |
| **Coreografía** | Cada servicio reacciona a los eventos que le interesan | Máximo desacoplamiento, pero nadie conoce el flujo completo: difícil de razonar y de depurar |
| **Orquestación** | Un coordinador dirige el proceso paso a paso | Flujo explícito y observable, a cambio de un punto central de acoplamiento |

Ninguno es superior: se eligen por proceso. Los procesos de negocio críticos y con compensaciones suelen pedir orquestación.

### Este sistema usa los dos, y en el sitio correcto

Vale la pena mirarlo porque es un ejemplo limpio de la distinción:

- **Coreografía en la frontera.** Quien publica `UserContactUpdated` en la cola `user-changes` no sabe que existe NotificationLog. Solo anuncia un hecho. Ese desacoplamiento es el que permite que mañana haya tres consumidores más sin tocar al productor.
- **Orquestación dentro.** `NotificationDispatchService` es un orquestador de libro: busca el trigger, resuelve las configuraciones activas, comprueba el destinatario, renderiza, envía y registra el resultado — en un orden explícito que se lee de arriba abajo en un solo archivo. Nadie tiene que reconstruir el flujo saltando entre siete consumidores.

```csharp title="El flujo orquestado, leído del propio NotificationDispatchService"
public async Task DispatchAsync(BusinessEvent businessEvent, CancellationToken ct)
{
    var trigger = await _triggers.GetByEventKeyAsync(EventKey.Create(businessEvent.EventKey), ct);
    if (trigger is null || !trigger.IsEnabled) return;                    // 1. resolver trigger

    var recipient = await _recipients.GetByIdAsync(businessEvent.RecipientId, ct);
    if (recipient is null) return;                                        // 2. resolver destinatario

    foreach (var configuration in trigger.ResolveActiveConfigurations())  // 3. por cada canal activo
        await DispatchConfigurationAsync(businessEvent, trigger.EventKey.Value,
            configuration, recipient, ct);
}

// Y dentro de DispatchConfigurationAsync, el resto de la tuberia:
//   4. puede el destinatario recibir por este canal?
//   5. cargar plantilla y version actual
//   6. renderizar  -> si falla: RecordNotificationFailure y seguir con el siguiente canal
//   7. enviar      -> si falla: RecordNotificationFailure; si va: RecordNotificationSuccess
```

<Callout kind="concepto" title="Por qué la mezcla es la decisión correcta aquí">

La ingesta necesita desacoplamiento máximo: los sistemas que publican hechos de negocio no deben saber nada de plantillas ni de canales. El despacho necesita lo contrario: es un proceso con pasos, con fallos parciales por canal y con un registro auditable de qué pasó — justo lo que la coreografía vuelve opaco. Cada tramo eligió el modelo que su problema pedía.

</Callout>

## 3.4 · Otros estilos que conviene conocer

| Estilo | Qué es | Cuándo |
| --- | --- | --- |
| Pipes and filters | Transformaciones encadenadas, cada una ignorante de la anterior | Pipelines de datos y procesamiento por lotes |
| Streaming | Procesamiento continuo sobre flujos con ventanas temporales | Métricas, detección de patrones, agregaciones en vivo |
| Serverless / FaaS | Unidades efímeras gestionadas por el proveedor | Cargas irregulares y trabajo por eventos; sufre con arranques en frío, límites de tiempo y acoplamiento al proveedor |
| Space-based | Replicación en memoria para picos extremos | Nicho, pero ilustra bien el trade-off memoria/consistencia |

El primero aparece dentro de este sistema aunque nadie lo llame así: *evento → resolver trigger → renderizar → enviar → registrar* es una tubería de transformaciones donde cada paso solo conoce su entrada. Reconocer el patrón importa porque sugiere dónde cortar si algún día ese flujo tuviera que partirse en piezas desplegables por separado.

## 3.5 · Cómo elegir un estilo

Se elige por atributos de calidad priorizados. Método simple y suficiente para un equipo:

<ol class="ddd-steps">
    <li>Lista los tres atributos de calidad prioritarios del sistema, con número (módulo 1).</li>
    <li>Puntúa dos o tres estilos candidatos contra ellos — una tabla basta, no hace falta ponderación fina.</li>
    <li>Escribe un ADR con el resultado <strong>y con lo que se sacrifica</strong>.</li>
</ol>

Si el ADR no dice qué se sacrifica, el análisis está incompleto. Ese es el filtro más útil que puedes aplicar a cualquier propuesta, incluida la tuya.

| Atributo priorizado | Monolito modular (actual) | Servicio de notificaciones separado |
| --- | --- | --- |
| Time-to-market con un equipo pequeño | Alto: un pipeline, un despliegue | Bajo: dos pipelines y un contrato que mantener |
| Aislamiento de fallo del envío | Medio: un envío lento consume hilos del mismo proceso que sirve la API | Alto: el panel sigue respondiendo aunque el despacho se atasque |
| Escalado independiente del consumo de colas | Bajo: escalas la API entera para escalar el consumo | Alto: escalas solo el consumidor |
| Coste operativo | Alto (a favor): un proceso, una base de datos | Bajo: otro despliegue, otra observabilidad, otro on-call |

Con los atributos que este proyecto tiene hoy —ninguno de disponibilidad escrito, un equipo, sin tráfico real— la columna izquierda gana sin discusión. La conversación cambiaría el día que exista un número en la fila "aislamiento de fallo": ahí es donde este sistema se partiría primero, y el corte natural ya está dibujado en el código, porque el consumo de colas está aislado en `Infrastructure/Messaging`.
