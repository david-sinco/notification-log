`NotificationLog.AppHost` es el punto de entrada para desarrollo: un proyecto de **.NET Aspire** que declara, en un único archivo (`AppHost.cs`), toda la infraestructura que el sistema necesita y cómo se conectan sus piezas entre sí. Ejecutarlo levanta contenedores Docker para cada dependencia y arranca ambos proyectos (`ApiService` y `Web`) ya apuntando a ellos — sin instalar SQL Server ni RabbitMQ a mano.

## Qué levanta, y para qué sirve cada cosa

- **SQL Server:** la base de datos real de `NotificationDbContext` — triggers, plantillas, destinatarios, notificaciones. Con volumen de datos persistente entre reinicios.
- **Redis:** cache de salida (*output cache*) para `NotificationLog.Web` — acelera respuestas del panel que no cambian entre pedidos.
- **RabbitMQ (con plugin de administración):** el bus de mensajería real (ver [página de Infraestructura](/arquitectura/infraestructura)). El plugin de administración expone una UI web, enlazada desde el propio dashboard de Aspire, para publicar mensajes de prueba a mano mientras se prueba la sincronización de destinatarios sin depender de que exista un productor real corriendo.
- **Buggregator:** el único sink de dev para todo lo que sale del servicio. Atrapa el SMTP saliente (puerto 1025, UI en el 8000) — lo que consume `SmtpEmailNotificationSender` — y en el mismo puerto 8000 expone un SMS Gateway que autodetecta el proveedor a partir del payload (`from`/`to`/`message`) sin necesidad de imitar la forma exacta de Twilio ni de ningún otro — lo que consume `HttpSmsNotificationSender`. La imagen trae más receptores (Sentry, Ray, Symfony VarDumper, Monolog, Inspector, XHProf, HTTP dumps), pero la variable `CLIENT_SUPPORTED_EVENTS=smtp,sms` los deja apagados — un módulo deshabilitado ni siquiera abre su puerto TCP, así que solo quedan los dos que este servicio usa de verdad. Reemplaza tanto a Mailpit como al antiguo contenedor de SmsPit — un contenedor menos que levantar, y un solo lugar donde validar cualquier notificación saliente. No tiene un paquete de hosting de Aspire dedicado, así que se agrega como contenedor genérico apuntando a `ghcr.io/buggregator/server`.

```csharp title="AppHost.cs (extracto, con los comentarios originales)"
var cache = builder.AddRedis("cache");

var sql = builder.AddSqlServer("sql").WithDataVolume();
var notificationDb = sql.AddDatabase("Default", "NotificationLog");

// Management plugin: UI en el puerto expuesto por Aspire (link visible en el dashboard) para
// publicar mensajes de prueba a mano mientras se prueba el ejemplo de Recipients sync.
var rabbitmq = builder.AddRabbitMQ("rabbitmq").WithManagementPlugin();

// Buggregator: un único sink de dev para todo lo que sale del servicio — SMTP
// (IEmailNotificationSender) y el SMS Gateway multi-proveedor, ambos por el mismo puerto 8000
// (ISmsNotificationSender). Reemplaza a Mailpit y a smspit. CLIENT_SUPPORTED_EVENTS limita los
// módulos activos a smtp+sms — un módulo deshabilitado ni siquiera abre su puerto TCP, por eso no
// se declaran endpoints para var-dump ni monolog (los demás módulos de la imagen: Sentry, Ray,
// VarDumper, Monolog, Inspector, XHProf, HTTP dumps). Sin paquete de hosting de Aspire dedicado,
// se agrega como contenedor genérico con los puertos default de la imagen.
var buggregator = builder.AddContainer("buggregator", "ghcr.io/buggregator/server")
    .WithEnvironment("CLIENT_SUPPORTED_EVENTS", "smtp,sms")
    .WithHttpEndpoint(port: 8000, targetPort: 8000, name: "ui")
    .WithEndpoint(port: 1025, targetPort: 1025, name: "smtp", scheme: "tcp");

var apiService = builder.AddProject<Projects.NotificationLog_ApiService>("apiservice")
    .WithHttpHealthCheck("/health")
    .WithReference(notificationDb).WaitFor(notificationDb)
    .WithReference(rabbitmq).WaitFor(rabbitmq)
    .WaitFor(buggregator);
```

<Callout kind="honesto" title="IEmailNotificationSender, ISmsNotificationSender e IPushNotificationSender ya tienen implementación">

`Infrastructure/Notifications/Sending` ya trae `SmtpEmailNotificationSender` y `HttpSmsNotificationSender`, ambos contra Buggregator en dev. `HttpPushNotificationSender` también existe, pero apunta a un placeholder porque todavía no hay un simulador de push en el AppHost — ni un proveedor real elegido. Cada uno se configura desde su propio objeto bajo `Notifications` en `appsettings` (`Notifications:Email`, `Notifications:Sms`, `Notifications:Push`). `IWhatsAppNotificationSender` sí está registrado, pero con un stub que siempre falla a propósito — no hay proveedor de WhatsApp elegido todavía.

</Callout>

## Lo que Aspire aporta gratis: salud, trazas y descubrimiento

Cada proyecto ejecutable llama a `AddServiceDefaults()` desde `NotificationLog.ServiceDefaults`, que en una sola línea agrega OpenTelemetry (trazas y métricas), health checks en `/health` y `/alive`, descubrimiento de servicios (para que `https+http://apiservice` se resuelva solo) y reintentos automáticos en llamadas HTTP salientes. El AppHost usa esos health checks para esperar (`WaitFor`) a que cada dependencia esté realmente lista antes de arrancar lo que depende de ella — evita que `ApiService` intente migrar la base de datos antes de que SQL Server termine de iniciar.

<Callout kind="ejercicio" title="Verlo correr">

El dashboard de Aspire (que se abre solo al ejecutar el AppHost) es el mejor lugar para confirmar todo lo de esta página: lista cada recurso, su estado, sus logs en vivo, y enlaces directos a la UI de administración de RabbitMQ, a Buggregator y a Scalar — sin memorizar un solo puerto.

</Callout>
