<Callout kind="concepto" title="Objetivos de este módulo">

- Verificar la regla de dependencia leyendo un `.csproj`, no confiando en un diagrama.
- Seguir un mensaje de mensajería desde su entrada hasta el dominio, capa por capa.
- Entender por qué este proyecto separa comandos de consultas sin usar un mediador.

</Callout>

<Callout kind="concepto" title="Concepto: dos nombres para la misma familia">

El dominio ocupa el centro y no depende de nada. Todo lo externo (HTTP, base de datos, colas) entra o sale por interfaces implementadas fuera del dominio. La regla operativa es la **regla de dependencia**: las dependencias apuntan hacia dentro. Beneficio real: el dominio se testea sin levantar nada.

Esa idea tiene dos nombres históricos casi intercambiables. **Hexagonal / Puertos y Adaptadores** (Cockburn, 2005) llama *puertos* a las interfaces del núcleo y *adaptadores* a sus implementaciones externas, sin capas internas nombradas. **Clean Architecture** (Robert C. Martin, 2012) — que el propio autor describe como una síntesis posterior de Hexagonal, Onion Architecture y DCI — sí nombra capas concéntricas explícitas: *Entities*, *Use Cases*, *Interface Adapters*, *Frameworks & Drivers*. Este proyecto, con capas nombradas `Domain`/`Application`/`Infrastructure`/`API`, se parece más a la segunda; sus repositorios e interfaces de envío usan el vocabulario de la primera. Vale la pena conocer ambos nombres en vez de tratarlos como sinónimos sin más.

</Callout>

## Cuatro capas, verificables en segundos

No hace falta confiar en un diagrama para saber si un proyecto realmente respeta la regla de dependencia: se abre el `.csproj` del dominio y se cuentan sus referencias.

```csharp title="NotificationLog.NotificationService.Domain.csproj (completo)"
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>
```

Sin Entity Framework, sin FluentValidation, sin ASP.NET, sin Protobuf. Solo el SDK base de .NET. Esa es la regla de dependencia hecha archivo de proyecto, no solo convención de carpetas: el propio compilador impediría que `Domain` referenciara `Infrastructure` aunque alguien lo intentara por error.

## La mensajería no existe en el dominio

La prueba más contundente de la regla de dependencia está en cómo entra un mensaje del bus de mensajería al sistema. No hay ningún tipo Protobuf ni ninguna referencia al cliente de mensajería dentro de `Domain`. El consumer vive en `Infrastructure`, traduce el mensaje a un comando de `Application`, y **solo entonces** se llama al dominio — con tipos propios (`UserChange`), no con el mensaje crudo. Ya viste el detalle completo en el [módulo de Context Map](/ddd/context-map); aquí es la misma historia contada desde el ángulo de la arquitectura, no de la integración.

## El borde exterior también traduce: DomainException → HTTP

La regla de dependencia también se cumple en la dirección contraria: el dominio no sabe qué es un código de estado HTTP. Es `GlobalExceptionHandler`, en la capa API, quien traduce `DomainException` a un `422` con el título "Regla de negocio violada" — el dominio nunca decide cómo se comunica su propio error al mundo exterior.

```csharp title="ApiService/Exceptions/GlobalExceptionHandler.cs (extracto)"
public async ValueTask<bool> TryHandleAsync(HttpContext context, Exception exception, CancellationToken ct)
{
    var problem = exception switch
    {
        NotFoundException e => new ProblemDetails { Status = 404, Title = "Recurso no encontrado", Detail = e.Message },
        AppValidationException e => BuildValidationProblem(e),

        DomainException e => new ProblemDetails
        {
            Status = StatusCodes.Status422UnprocessableEntity,
            Title = "Regla de negocio violada",   // <- el dominio nunca supo que esto sería un 422
            Detail = e.Message
        },

        _ => null
    };
    // ...
}
```

## CQRS: comandos y consultas, sin mediador

<Callout kind="concepto" title="Concepto: CQRS">

Separar el modelo de escritura (agregados, invariantes) del modelo de lectura (proyecciones optimizadas para consultas). No requiere event sourcing ni dos bases de datos: empezar separando comandos de queries en el mismo esquema ya aporta.

</Callout>

Cada operación de `Triggers` vive en su propia carpeta con su propio comando y su propio handler — no hay una clase `TriggerService` con quince métodos. Tampoco hay un mediador de por medio: cada endpoint inyecta directamente el handler que necesita.

```csharp title="Endpoints/TriggerEndpoints.cs (comando inyectado directo)"
group.MapPost("/", CreateAsync)
    .WithName("CreateTrigger")
    .Produces<CreatedTriggerResponse>(StatusCodes.Status201Created)
    .ProducesProblem(StatusCodes.Status422UnprocessableEntity);

private static async Task<IResult> CreateAsync(
    CreateTriggerRequest body,
    CreateTriggerHandler handler,     // <- inyectado directo, sin mediador
    CancellationToken ct)
{
    var id = await handler.HandleAsync(new CreateTriggerCommand(body.EventKey, body.Description), ct);
    return Results.CreatedAtRoute("GetTriggerById", new { id }, new CreatedTriggerResponse(id));
}
```

## Capa de aplicación: orquesta, no decide

<Callout kind="concepto" title="Concepto: capa de aplicación">

Orquesta: carga agregados, invoca comportamiento de dominio, gestiona la transacción. No contiene reglas de negocio. Un application service ideal tiene entre 5 y 15 líneas. Si tiene condicionales de negocio, esa lógica pertenece al dominio.

</Callout>

`CreateTriggerHandler` cumple esa métrica casi al pie de la letra: valida la forma del comando, construye el value object `EventKey`, comprueba unicidad contra el repositorio, delega la creación real al agregado (`NotificationTrigger.Create`) y guarda. Casi ningún `if` propio: el formato del event key lo impone `EventKey.Create` y la descripción, `NotificationTrigger.Create`.

Queda uno, y conviene no barrerlo bajo la alfombra: la comprobación de unicidad (`ExistsAsync`) **sí es una regla de negocio**, y vive en el handler. No puede vivir en el agregado, porque ningún `NotificationTrigger` conoce a los demás triggers — y esa imposibilidad es exactamente la señal que identifica una regla que cruza agregados. El [módulo 13](/ddd/pruebas) la retoma como el caso claro de test de capa de aplicación, y el [módulo 12](/ddd/persistencia) muestra por qué, además, necesita un índice único detrás para sobrevivir a dos peticiones simultáneas.

```csharp title="Application/Triggers/Commands/CreateTrigger/CreateTriggerHandler.cs"
public sealed class CreateTriggerHandler
{
    public async Task<Guid> HandleAsync(CreateTriggerCommand cmd, CancellationToken ct)
    {
        await _validator.ValidateAndThrowAppAsync(cmd, ct);           // forma del mensaje

        var eventKey = EventKey.Create(cmd.EventKey);                 // regla del value object

        if (await _triggers.ExistsAsync(eventKey, ct))                // regla entre agregados (unicidad)
            throw new AppValidationException($"Ya existe un trigger para '{eventKey}'.");

        var trigger = NotificationTrigger.Create(eventKey, cmd.Description);  // regla del agregado

        await _triggers.AddAsync(trigger, ct);
        await _uow.SaveChangesAsync(ct);

        return trigger.Id;
    }
}
```

<Callout kind="ejercicio" title="Ejercicio para pensar">

Cuenta las líneas de `CreateTriggerHandler.HandleAsync` sin contar llaves ni líneas en blanco. Después haz lo mismo con el método más largo de tu propia capa de aplicación. Si el tuyo supera ampliamente esa cifra, casi seguro hay una regla de negocio escondida ahí que debería vivir dentro de un agregado.

</Callout>
