## Concepto

Una entidad es un objeto con identidad propia que persiste a lo largo del tiempo, aunque cambien todos sus atributos. Un pedido sigue siendo el mismo pedido tras cambiar de estado, dirección e importe.

La identidad **no** es "tiene un id en base de datos": es que el negocio distingue a *ese* individuo de cualquier otro con los mismos datos. Y la entidad protege sus propias reglas: no expone setters públicos, expone comportamiento con nombre de negocio.

| | Value Object | Entidad |
| --- | --- | --- |
| **Igualdad** | Por valores | Por identidad (`Id`) |
| **Mutabilidad** | Inmutable | Cambia con el tiempo |
| **Tipo en C#** | `sealed record` | `class` que hereda de `Entity` |
| **Pregunta clave** | "¿cuánto vale?" | "¿cuál es?" |

## Igualdad por identidad, no por valores

La forma más precisa de ver la diferencia es leer cómo cada uno implementa la igualdad. Todas las entidades de los dos servicios de este repositorio heredan de la misma clase base compartida:

<Code
    code={whole(entitySource)}
    lang="csharp"
    title="Shared/Domain.Shared/Common/Entity.cs"
    mark={['return Id == other.Id;']}
/>

La última línea es la definición entera del patrón: dos entidades son iguales **si y solo si tienen el mismo `Id`**, sin mirar un solo campo más.

Repara además en el comentario del código: *"dos entidades sin persistir nunca son iguales entre sí"*. Es una decisión deliberada — tratar como iguales a dos objetos sin identidad asignada, solo porque coinciden sus atributos, sería mezclar identidad con valores, que es exactamente lo que una entidad existe para evitar.

<Callout kind="honesto" title="Esa guarda, hoy, no llega a dispararse en el dominio de Notifications">

Si intentas provocar el caso, no podrás: ningún agregado de Notifications llega nunca a existir con `Id == Guid.Empty`. `Recipient.Create` exige el `userId` y lo rechaza si viene vacío; `NotificationTrigger.Create`, `NotificationTemplate.Create` y `Notification` asignan `Guid.NewGuid()` en la propia fábrica. **La identidad se decide en el dominio, no la genera la base de datos.**

La guarda existe para el caso general —entidades cuyo id asigna el motor al insertar, donde sí hay una ventana con `Id` vacío— y aquí funciona como red de seguridad, no como caso vivo. Es un buen ejemplo de código defensivo heredado de una clase base genérica: correcto, pero no ejercitado por este modelo concreto.

</Callout>

<Callout kind="honesto" title="Esa clase base es compartida — y eso tiene nombre">

`Entity` vive en `Shared/Domain.Shared`, y la usan tanto Notifications como Rentals. Eso es un **Shared Kernel** ([módulo 4](/ddd/context-map)): código de dominio compartido entre dos bounded contexts.

Es el patrón más peligroso del Context Map, porque cualquier cambio ahí afecta a los dos contextos a la vez. Aquí está justificado por lo que contiene: **conceptos estructurales de DDD** (`Entity`, `AggregateRoot`, `DomainException`, `IDomainEvent`), no reglas de negocio. Si algún día alguien mete una regla de notificaciones en `Domain.Shared`, ese será el momento de partirlo.

</Callout>

## Entidades que no son la raíz: TemplateVersion

No toda entidad es un agregado raíz. `TemplateVersion` también hereda de `Entity` —tiene su propio `Id`, distinto en cada versión— pero solo se puede crear y retirar *a través de* `NotificationTemplate`, nunca de forma independiente.

<Code
    code={member(templateVersionSource, 'internal static TemplateVersion Create') + '\n\n' + member(templateVersionSource, 'internal void Retire')}
    lang="csharp"
    title="Services/Notification/.../Templates/TemplateVersion.cs · fábrica y mutación, ambas internal"
    mark={['internal static TemplateVersion Create', 'internal void Retire']}
/>

El modificador `internal` no es un detalle estilístico: es **el compilador de C# impidiendo** que código de `Application` o `Infrastructure` cree o mute una versión suelta. Dentro del propio ensamblado `Domain` la garantía es de convención, no del compilador — hoy solo `NotificationTemplate` la invoca, pero nada impediría que otra clase del mismo ensamblado lo hiciera.

Esa es, de hecho, la frontera real que protege `internal`: **entre capas, no dentro de una misma capa**.

<Callout kind="advertencia" title="Entidad no es sinónimo de 'tabla con Id'">

El error clásico (antipatrón "Entidad = tabla") es pensar que cualquier fila con clave primaria es una entidad de dominio.

La prueba real es otra: **¿el negocio distingue este individuo de otro con los mismos valores, y le importa su ciclo de vida?** `TemplateVersion` lo cumple (la versión 2 no es lo mismo que la 3, aunque tuvieran el mismo texto). Una fila de una tabla de códigos de país, probablemente no — ahí un value object o un `enum` alcanza.

</Callout>

<Callout kind="resumen" title="Para recordar">

- Entidad = **igualdad por `Id`**. Value object = igualdad por valores. Todo lo demás se deriva de ahí.
- La identidad de este dominio **se decide en la fábrica**, no la genera la base de datos.
- Una entidad no expone setters: expone **métodos con nombre de negocio** que mutan su estado.
- No toda entidad es raíz. `TemplateVersion` existe solo dentro de `NotificationTemplate`, y `internal` lo hace cumplir entre capas.
- `Entity` en `Domain.Shared` es un **Shared Kernel** justificado porque contiene estructura, no reglas.

</Callout>

<Callout kind="ejercicio" title="Comprueba que lo entendiste">

1. Dos `TemplateVersion` distintas tienen exactamente el mismo `Subject` y `Body`. ¿`Equals` devuelve `true`? ¿Y dos `TemplateName` con el mismo texto?
2. `TemplateVersion.Create` es `internal`. Desde un proyecto externo, ¿cómo llegas a una plantilla con dos versiones? (Pista: solo hay un camino, y es el bueno.)
3. Para cada clase de tu dominio que hoy tenga un `Id`: si dos instancias tuvieran los mismos valores en todos los demás campos, ¿el negocio las trataría como la misma cosa o como dos? Si es "dos", necesita `Equals` por identidad.

</Callout>
