- Distinguir igualdad por identidad de igualdad por valores.
- Leer `Entity.Equals` y explicar cada línea.
- Identificar una entidad que no es raíz de agregado, y qué la protege.

</Callout>

## Concepto

Una entidad es un objeto con identidad propia que persiste a lo largo del tiempo, aunque cambien todos sus atributos. Un pedido sigue siendo el mismo pedido tras cambiar de estado, dirección e importe. La identidad no es "tiene un id en base de datos": es que el negocio distingue a *ese* individuo de cualquier otro con los mismos datos. La entidad protege sus propias reglas; no expone setters públicos, expone comportamiento con nombre de negocio.

## Igualdad por identidad, no por valores

La forma más precisa de ver la diferencia entre una entidad y un value object es leer cómo cada uno implementa la igualdad. Todas las entidades del dominio heredan de `Entity`, que sobreescribe `Equals` para comparar solo por `Id` — nunca por los demás campos:

```csharp title="Domain/Common/Entity.cs"
public abstract class Entity
{
    public Guid Id { get; protected set; }

    protected Entity() { }
    protected Entity(Guid id) => Id = id;

    public override bool Equals(object? obj)
    {
        if (obj is not Entity other) return false;
        if (ReferenceEquals(this, other)) return true;
        if (GetType() != other.GetType()) return false;

        // Dos entidades sin persistir nunca son iguales entre sí
        if (Id == Guid.Empty || other.Id == Guid.Empty) return false;

        return Id == other.Id;
    }

    public override int GetHashCode() => (GetType(), Id).GetHashCode();

    public static bool operator ==(Entity? left, Entity? right) => Equals(left, right);
    public static bool operator !=(Entity? left, Entity? right) => !Equals(left, right);
}
```

Repara en el comentario del código: *"dos entidades sin persistir nunca son iguales entre sí"*. Es una decisión deliberada: tratar como iguales a dos objetos sin identidad asignada, solo porque coinciden sus atributos, sería mezclar identidad con valores — exactamente lo que una entidad existe para evitar.

<Callout kind="honesto" title="Esa guarda, hoy, no llega a dispararse en este dominio">

Si intentas provocar el caso, no podrás: ningún agregado de este repositorio llega nunca a existir con `Id == Guid.Empty`. `Recipient.Create` exige el `userId` y lo rechaza si viene vacío; `NotificationTrigger.Create`, `NotificationTemplate.Create` y `Notification` asignan `Guid.NewGuid()` en la propia fábrica. La identidad se decide *en el dominio*, no la genera la base de datos.

La guarda existe para el caso general —entidades cuyo id lo asigna el motor al insertar, donde sí hay una ventana con `Id` vacío— y aquí funciona como red de seguridad, no como caso vivo. Vale la pena saberlo: es un buen ejemplo de código defensivo heredado de una clase base genérica, correcto pero no ejercitado por este modelo concreto.

</Callout>

## Recipient: mismo Id, atributos que cambian

`Recipient` (que ya viste en el [módulo 3](/ddd/bounded-context)) es el ejemplo más claro de entidad-como-raíz: su `Id` es el mismo `userId` que llega del contexto de Usuarios, y a lo largo de su vida cambia de nombre, de email, de teléfono, de zona horaria, se activa y se desactiva — pero sigue siendo el mismo `Recipient` para el negocio. Ningún método permite reemplazar el `Id`; todos los métodos mutan atributos manteniendo la identidad fija.

```csharp title="Domain/Recipients/Recipient.cs (extracto de comportamiento)"
public void ChangeEmail(string? email) => Email = NormalizeEmail(email);

public void ChangePhone(string? phone) => Phone = NormalizePhone(phone);

public void Activate() => IsActive = true;

public void Deactivate() => IsActive = false;

// El Id nunca cambia: no existe ChangeId() ni un setter público sobre Id.
// La identidad del Recipient es fija desde Create(userId, ...).
```

## Entidades que no son la raíz: TemplateVersion

No toda entidad es un agregado raíz. `TemplateVersion` también hereda de `Entity` — tiene su propio `Id`, distinto en cada versión — pero solo se puede crear y retirar *a través de* `NotificationTemplate`, nunca de forma independiente. El modificador `internal` en sus métodos de fábrica y de mutación no es un detalle estilístico: es el compilador de C# impidiendo que código de `Application` o `Infrastructure` cree o mute una versión suelta. Dentro del propio ensamblado `Domain` la garantía es de convención, no del compilador — hoy solo `NotificationTemplate` la invoca, pero nada impediría que otra clase del mismo ensamblado lo hiciera. Esa es, de hecho, la frontera real que protege `internal`: entre capas, no dentro de una misma capa.

Ese modificador tiene una consecuencia práctica que se siente al escribir el primer test: un proyecto de pruebas externo tampoco puede llamar a `TemplateVersion.Create`, así que está obligado a llegar a cualquier estado por la misma API pública que usa el código de producción. Es una restricción incómoda al principio y una ventaja después — el [módulo 13](/ddd/pruebas) explica por qué, y por qué la salida fácil (`InternalsVisibleTo`) suele costar más de lo que ahorra.

```csharp title="Domain/Templates/TemplateVersion.cs (fábrica y mutación)"
public sealed class TemplateVersion : Entity
{
    internal static TemplateVersion Create(
        int number, string? subject, string body, NotificationChannel channel)
        => new()
        {
            Id = Guid.NewGuid(),
            Number = number,
            Subject = NormalizeSubject(subject, channel),
            Body = NormalizeBody(body),
            IsCurrent = true,
            CreatedAt = DateTime.UtcNow
        };

    internal void Retire() => IsCurrent = false;

    // Create y Retire son 'internal': solo código del mismo ensamblado (Domain) puede
    // invocarlos, y en la práctica solo NotificationTemplate lo hace. El compilador
    // impide crear una versión "suelta", fuera del agregado que la posee.
}
```

<Callout kind="advertencia" title="Entidad no es sinónimo de 'tabla con Id'">

El error clásico (antipatrón "Entidad = tabla") es pensar que cualquier fila con clave primaria es una entidad de dominio. La prueba real es otra: ¿el negocio distingue este individuo de otro con los mismos valores, y le importa su ciclo de vida? Un `TemplateVersion` lo cumple (versión 2 no es lo mismo que versión 3, aunque tuvieran el mismo texto). Una fila de una tabla de configuración estática de códigos de país, probablemente no — ahí un value object o un simple `enum` alcanza.

</Callout>

<Callout kind="ejercicio" title="Ejercicio para pensar">

Para cada clase de tu propio dominio que hoy tenga un `Id`, pregúntate: si dos instancias tuvieran exactamente los mismos valores en todos los demás campos, ¿el negocio las trataría como la misma cosa o como dos cosas distintas? Si la respuesta es "dos cosas distintas", es una entidad y necesita `Equals` por identidad, no por valores — igual que `Entity` en este repositorio.

</Callout>
