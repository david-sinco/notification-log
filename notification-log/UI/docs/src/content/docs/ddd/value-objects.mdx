## Concepto

Un Value Object es un objeto definido por sus atributos, sin identidad propia, inmutable y auto-validado. Dos instancias con el mismo valor son intercambiables: no importa *cuál* es, importa *cuánto* vale.

Sus tres ganancias prácticas:

<ol class="ddd-steps">
    <li><strong>Elimina la validación duplicada.</strong> Un valor inválido no puede llegar a existir, así que nadie tiene que volver a comprobarlo.</li>
    <li><strong>Elimina el error de confundir dos primitivos del mismo tipo.</strong> El compilador no deja pasar un <code>EventKey</code> donde va un <code>TemplateName</code>.</li>
    <li><strong>Da un sitio natural donde colgar comportamiento</strong> relacionado con ese valor (normalizar, formatear, comparar).</li>
</ol>

Las dos líneas marcadas son el patrón entero:

- **`Create` estático.** Nunca devuelve un valor a medio validar: o lanza `DomainException`, o devuelve algo correcto.

Una vez que tienes un `TemplateName` en la mano, sabes con certeza —sin volver a comprobar nada— que está en minúsculas, tiene el formato correcto y no supera los 100 caracteres. **Esa garantía es el valor real del patrón.**

## Por qué `record` y no `class`

Ambos son `sealed record`, no `class`. Los *records* de C# generan automáticamente igualdad por valor (dos instancias con el mismo `Value` son iguales) y son inmutables por convención con propiedades `{ get; }`.

Es el tipo de dato del lenguaje que más se parece a la definición de libro de un Value Object, sin escribir `Equals` ni `GetHashCode` a mano. Compáralo con [`Entity`](/ddd/entidades), que compara por `Id` precisamente porque es lo contrario.

Las ganancias 1 y 2 se ven en `EventKey`. La tercera —dar un sitio donde colgar comportamiento— se ve mejor en el otro servicio de este repositorio. `Money`, en Rentals, además de impedir importes negativos sabe **cómo se escribe un valor en pesos colombianos**:

/>

Ese `ToString` es la diferencia entre un value object y una simple validación: el mensaje de error *"El canon mínimo de arriendo es $300.000"* sale gratis en cualquier parte del dominio, porque el tipo sabe presentarse a sí mismo.

Fíjate también en `FromStorage`, que es `internal` y **no valida**: es la puerta que usa la persistencia para reconstruir un valor que ya se validó cuando entró. Dos puertas, dos propósitos, y solo una pública.

## Cuándo NO hace falta un Value Object

No todo lo que podría ser un Value Object lo es —y eso también es información útil.

`NotificationChannel` es un `enum` simple (`Email`, `Sms`, `Push`, `WhatsApp`): una forma legítima y más liviana de resolver el mismo problema (evitar strings mágicos) cuando el conjunto de valores es **cerrado** y no necesita validación de formato. Un value object ahí sería ceremonia sin beneficio.

La regla práctica: si el conjunto de valores válidos se puede enumerar, un `enum` gana. Si hay que validar una *forma*, hace falta un value object.

Dos constantes independientes para el mismo concepto, libres de divergir el día que alguien cambie una sola de las dos. Es obsesión primitiva de manual, y está **dentro del dominio**, no en el borde.

Merece la pena verlo porque enseña algo incómodo: adoptar el patrón no es una decisión que se toma una vez, es una disciplina que se sostiene archivo por archivo. El [módulo 12](/ddd/persistencia) celebra —con razón— que `EventKey.MaxLength` mande sobre el esquema en la tabla de triggers; en la tabla de notificaciones, esa misma regla se escribió a mano por segunda vez.

<Callout kind="advertencia" title="Dónde sí es correcto que haya un string">

Cuidado con la conclusión demasiado entusiasta. `BusinessEvent.EventKey` **también** es un `string`, y ahí está bien: es el dato que entra desde fuera, todavía sin validar. El borde del sistema es exactamente el sitio donde un primitivo es honesto, y `EventKey.Create` es la puerta que lo convierte en un valor confiable.

La regla: **primitivo antes de la puerta, value object después**. El defecto de `Notification` es que está después de la puerta y sigue siendo primitivo.

</Callout>

<Callout kind="resumen" title="Para recordar">

- El molde es siempre el mismo: **`sealed record` + constructor privado + `Create` estático que valida**.
- La ganancia no es "validar": es que **después de `Create` nadie tiene que volver a validar**.
- `record` da igualdad por valor gratis. Eso es exactamente lo que distingue un VO de una entidad.
- Si el conjunto de valores es cerrado y enumerable, un **`enum` basta**. No todo merece un tipo.
- Un VO también es el sitio natural para el comportamiento del valor (`Money.ToString`).
- **Primitivo antes de la puerta de entrada, value object después.**

</Callout>
