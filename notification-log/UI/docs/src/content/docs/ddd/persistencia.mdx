<Callout kind="concepto" title="Objetivos de este módulo">

- Reconocer las cuatro técnicas con las que este repositorio mapea agregados encapsulados a tablas SQL.
- Explicar por qué `IUnitOfWork` tiene un solo método y quién lo implementa.
- Distinguir consistencia fuerte (dentro del agregado) de eventual (entre agregados) señalando el código de cada una.
- Encontrar, con un escenario concreto, la invariante que hoy *no* está protegida bajo concurrencia — y decidir qué costaría cerrarla.

</Callout>

**Para quién es:** ya leíste los módulos [7 (Agregados)](/ddd/agregados) y [9 (Repositorios)](/ddd/repositorios-y-factories), y sabes que `NotificationTrigger` protege su invariante de canal único con campos privados y setters privados. Este módulo responde la pregunta que queda abierta al final de aquellos dos: *si nada de eso es público, ¿cómo demonios lo guarda y lo reconstruye Entity Framework Core?* — y, sobre todo, qué pasa cuando dos peticiones hacen eso a la vez.

## El problema: el ORM y el agregado quieren cosas opuestas

Un ORM, en su forma más cómoda, quiere una clase con constructor público sin argumentos, propiedades con `get; set;` públicos y colecciones `List<T>` también públicas y reasignables. Necesita poder crear la instancia vacía y rellenarla campo por campo. Un agregado quiere exactamente lo contrario: nacer solo a través de una fábrica que valida, no dejar mutar nada salvo por métodos con nombre de negocio, y no dejar que nadie agregue elementos a su colección de hijos saltándose `AddConfiguration`.

Esa tensión tiene tres desenlaces posibles, y solo uno es aceptable. El primero es rendirse y abrir el modelo (setters públicos "porque EF los necesita"): así nace el **modelo anémico causado por el ORM**, el más común de todos, porque llega disfrazado de restricción técnica. El segundo es mantener el modelo cerrado y construir a mano una capa de traducción entre entidades de dominio y entidades de persistencia: correcto, pero caro — el doble de clases y un mapeo que mantener. El tercero, el que usa este repositorio, es **enseñarle al ORM a entrar por la puerta de atrás**: dejarle acceder a campos privados y a constructores privados mediante configuración externa, sin abrir un solo miembro público que el negocio no necesite.

<Callout kind="antipatron" title="El antipatrón, dicho con el ejemplo de este dominio">

Imagina que `NotificationTrigger` tuviera `public List<NotificationConfiguration> Configurations { get; set; }` "porque EF lo pide". La invariante del módulo 7 desaparece en el acto: cualquier handler podría hacer `trigger.Configurations.Add(...)` sin pasar por `EnsureChannelIsFree`, y el sistema aceptaría dos configuraciones de Email activas para el mismo evento. El agregado seguiría *pareciendo* un agregado — misma clase, mismos métodos — pero ya no protegería nada. Por eso la propiedad real es `IReadOnlyCollection<NotificationConfiguration> Configurations => _configurations.AsReadOnly();` sobre un campo privado.

</Callout>

## Las cuatro técnicas, en archivos reales

Todo el trabajo de traducción vive en `Infrastructure/Persistence/Configuration/`: seis clases `IEntityTypeConfiguration<T>`, todas `internal`, que `NotificationDbContext` recoge con `ApplyConfigurationsFromAssembly`. El dominio no se entera de que existen.

### 1 · Constructor privado para el ORM, fábrica pública para el negocio

Los cuatro agregados y las dos entidades hijas declaran un constructor sin argumentos privado o protegido, con un comentario que dice para qué está. EF Core lo usa por reflexión al materializar una fila; ningún código de negocio puede invocarlo. Es la misma idea que viste en el [módulo 9](/ddd/repositorios-y-factories) como "dos caminos de creación que nunca se cruzan", ahora vista desde el lado de la persistencia.

```csharp title="Domain/Recipients/Recipient.cs y Domain/Triggers/NotificationConfiguration.cs"
// Domain/Recipients/Recipient.cs
public sealed class Recipient : AggregateRoot
{
    private readonly Dictionary<string, string> _attributes = new();

    public string Name { get; private set; } = default!;   // setter privado
    public bool IsActive { get; private set; }

    public IReadOnlyDictionary<string, string> Attributes => _attributes;   // solo lectura

    private Recipient() { }   // EF Core

    public static Recipient Create(Guid userId, string name, string? email, string? phone) { /* valida */ }
}

// Domain/Triggers/NotificationConfiguration.cs
protected NotificationConfiguration() { }

internal static NotificationConfiguration Create(Guid templateId, NotificationChannel channel)
// ^ 'internal': ni siquiera Application puede crear una configuración suelta.
//   Solo NotificationTrigger.AddConfiguration, que antes llama a EnsureChannelIsFree.
```

### 2 · Colecciones: EF escribe en el campo, no en la propiedad

Aquí está la línea clave de todo el módulo. `NotificationTriggerConfiguration` declara la relación uno-a-muchos y después le ordena a EF Core que acceda a la navegación **por campo**, no por propiedad. Como el campo es `_configurations` (un `List<T>` privado) y la propiedad pública es un `IReadOnlyCollection` de solo lectura, EF puede rellenar la lista al cargar sin que exista jamás un setter público.

```csharp title="Infrastructure/Persistence/Configuration/NotificationTriggerConfiguration.cs"
builder.HasMany(t => t.Configurations)
    .WithOne()                                       // el hijo no tiene navegación de vuelta al padre
    .HasForeignKey("NotificationTriggerId")          // shadow property: no existe en la clase
    .OnDelete(DeleteBehavior.Cascade);

builder.Metadata
    .FindNavigation(nameof(NotificationTrigger.Configurations))!
    .SetPropertyAccessMode(PropertyAccessMode.Field);
// ^ La línea que lo hace posible: EF escribe en el campo _configurations,
//   no en la propiedad IReadOnlyCollection. El encapsulamiento queda intacto.
```

Nota también `.HasForeignKey("NotificationTriggerId")` con la clave foránea escrita como *string*: es una **shadow property**. La columna existe en la tabla `NotificationConfigurations`, pero no existe ninguna propiedad `NotificationTriggerId` en la clase `NotificationConfiguration`. Eso no es un truco: es la Regla 3 de Vernon aplicada hacia arriba. Un hijo no necesita saber el id de su padre para cumplir su función, y si no lo necesita, no se le pone. La base de datos sí lo necesita, y ese es problema de la base de datos.

### 3 · Value objects: una conversión declarada fuera del dominio

SQL Server no sabe qué es un `EventKey`. La conversión de ida y vuelta se declara en la configuración de EF, y la vuelta pasa por `EventKey.Create(value)` — es decir, el valor que sale de la base de datos **se revalida** con la misma regla de negocio que se aplicó al entrar. Y el tamaño de columna reutiliza `EventKey.MaxLength`, la misma constante que usa el dominio: el esquema se deriva del modelo, nunca al revés.

```csharp title="Infrastructure/Persistence/Configuration/NotificationTriggerConfiguration.cs (conversión)"
builder.Property(t => t.EventKey)
    .HasConversion(
        key => key.Value,                // al guardar: EventKey -> string
        value => EventKey.Create(value)) // al leer: string -> EventKey, revalidado
    .HasColumnName("EventKey")
    .HasMaxLength(EventKey.MaxLength)    // la constante del dominio manda sobre el esquema
    .IsUnicode(false)
    .IsRequired();

builder.HasIndex(t => t.EventKey)
    .IsUnique()
    .HasDatabaseName("UX_NotificationTriggers_EventKey");
```

<Callout kind="advertencia" title="El coste real de un value converter, visible en este repositorio">

Un valor convertido deja de ser transparente para el proveedor de consultas. La comparación por igualdad sigue traduciéndose sin problema — `ExistsAsync` hace `_db.Triggers.AnyAsync(t => t.EventKey == eventKey, ct)` y eso se convierte en un `WHERE EventKey = @@p0` que aprovecha el índice único. Pero en cuanto quieres tratar el valor *como el string que es en la base de datos*, EF ya no puede mirar dentro del tipo convertido. Y este repositorio tiene la prueba en un archivo real: el `ListAsync` de triggers no puede escribir `EF.Functions.Like(t.EventKey.Value, pattern)`, así que baja un nivel y accede a la columna por nombre.

</Callout>

```csharp title="Infrastructure/Persistence/Repositories/NotificationTriggerRepository.cs (la vía de escape)"
public async Task<(IReadOnlyList<NotificationTrigger> Items, int TotalCount)> ListAsync(
    string? search, bool? isEnabled, int page, int pageSize, CancellationToken ct)
{
    var query = _db.Triggers
        .Include(t => t.Configurations)
        .AsNoTracking();

    if (!string.IsNullOrWhiteSpace(search))
    {
        var pattern = $"%{search.Trim()}%";
        query = query.Where(t =>
            EF.Functions.Like(EF.Property<string>(t, "EventKey"), pattern) ||   // <- por columna
            EF.Functions.Like(t.Description, pattern));                         // <- string normal
    }

    // ...y otra vez al ordenar, por el mismo motivo:
    var items = await query
        .OrderBy(t => EF.Property<string>(t, "EventKey"))
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .ToListAsync(ct);
}
```

`EF.Property<string>(t, "EventKey")` le dice al traductor de consultas "olvídate del tipo del modelo y usa la columna". Funciona, y aquí es la decisión correcta — pero fíjate en lo que se perdió: el nombre de la columna pasó a ser una cadena mágica que ningún compilador verifica, y ese mismo truco aparece dos veces, también en el `OrderBy`. Ese es el precio concreto del patrón, y conviene conocerlo antes de convertir todo lo que se mueve. Un value object gana seguridad en el dominio y la paga en el borde de las consultas.

### 4 · Lo que es parte del agregado pero no es una entidad: JSON

`Recipient.Attributes` y `Notification.Payload` son diccionarios libres. No son entidades — no tienen identidad ni ciclo de vida propio — así que no merecen una tabla hija con su repositorio y su tabla de unión. Son *valor* perteneciente al agregado, y se guardan como valor: una columna `nvarchar(max)` con JSON dentro. Otra vez, EF accede al campo privado `_attributes` e ignora la propiedad pública de solo lectura.

```csharp title="Infrastructure/Persistence/Configuration/RecipientConfiguration.cs (diccionario como JSON)"
builder.Ignore(r => r.Attributes);   // la propiedad pública de solo lectura no es una columna

var attributesComparer = new ValueComparer<Dictionary<string, string>>(
    (a, b) => (a ?? new()).SequenceEqual(b ?? new()),                       // ¿cambió?
    d => d.Aggregate(0, (hash, kv) => HashCode.Combine(hash, kv.Key, kv.Value)),
    d => new Dictionary<string, string>(d));                                // snapshot

builder.Property<Dictionary<string, string>>("_attributes")
    .HasField("_attributes")
    .UsePropertyAccessMode(PropertyAccessMode.Field)
    .HasColumnName("Attributes")
    .HasConversion(
        dict => JsonSerializer.Serialize(dict, (JsonSerializerOptions?)null),
        json => string.IsNullOrEmpty(json)
            ? new Dictionary<string, string>()
            : JsonSerializer.Deserialize<Dictionary<string, string>>(json, (JsonSerializerOptions?)null)!,
        attributesComparer)
    .IsRequired();
```

El `ValueComparer` no es decorativo. Sin él, EF compara diccionarios por referencia y nunca detecta que `SetAttribute("plan", "premium")` cambió algo: el objeto sigue siendo el mismo objeto en memoria, así que `SaveChangesAsync` no generaría ningún `UPDATE` y el cambio se perdería en silencio. El comparador le enseña a EF a comparar el contenido y a clonar el diccionario para guardar el snapshot original. Es el tipo de detalle que solo aparece cuando decides guardar valor en vez de entidades, y hay que pagarlo entero.

## Unidad de trabajo: una interfaz de un solo método

<Callout kind="concepto" title="Concepto: Unit of Work">

Agrupa un conjunto de cambios sobre uno o más objetos y los confirma como una sola transacción. En DDD, su valor no es "poder guardar varias cosas": es marcar con precisión *dónde termina la operación de negocio*, para que el límite transaccional coincida con el límite del agregado.

</Callout>

La abstracción real de este proyecto es deliberadamente mínima: vive en `Application/Abstractions/IUnitOfWork.cs` y tiene un método. La implementación no es una clase envolvente sino el propio `NotificationDbContext`, que ya expone `SaveChangesAsync`; el registro en el contenedor lo resuelve una lambda.

```csharp title="Application/Abstractions/IUnitOfWork.cs + Infrastructure/DependencyInjection.cs"
// Application/Abstractions/IUnitOfWork.cs — la abstracción entera
public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(CancellationToken ct);
}

// Infrastructure/Persistence/Context/NotificationDbContext.cs
public sealed class NotificationDbContext(DbContextOptions<NotificationDbContext> options)
    : DbContext(options), IUnitOfWork { /* ... */ }

// Infrastructure/DependencyInjection.cs — sin clase envolvente, solo una lambda
services.AddScoped<IUnitOfWork>(sp => sp.GetRequiredService<NotificationDbContext>());
```

La consecuencia de diseño importante es la que ya viste en el [módulo 7](/ddd/agregados), ahora con el mecanismo a la vista: cada handler de comando llama a `_uow.SaveChangesAsync(ct)` **una sola vez, al final**. Ese único punto es la transacción, y todo lo que se modificó antes de él pertenece a un solo agregado. Cuando `AddConfigurationHandler` lee un `NotificationTemplate` para validar, ese template entra al *change tracker* pero nadie lo muta, así que el `SaveChanges` no genera ningún `UPDATE` sobre él. La regla "una transacción, un agregado" no está escrita en ninguna parte: emerge de que solo un agregado cambió antes del único guardado.

## Consistencia fuerte dentro, eventual fuera

El límite del agregado es también el límite de lo que se garantiza consistente en el mismo instante. En este dominio eso se ve en dos lugares opuestos:

- **Fuerte, dentro:** `GetByIdAsync` y `GetByEventKeyAsync` del repositorio de triggers siempre hacen `.Include(t => t.Configurations)`. Nunca devuelven una raíz sin sus hijos, porque `EnsureChannelIsFree` necesita ver *todas* las configuraciones para decidir. Un agregado cargado a medias es un agregado que no puede defender su invariante.
- **Eventual, fuera:** `Notification` guarda `TemplateVersionId` como un `Guid` suelto. Nada impide que esa versión sea retirada (`TemplateVersion.Retire()`) cinco minutos después de haber enviado la notificación. Y está bien: el registro histórico apunta a la versión que se usó *entonces*, y su corrección no depende del estado actual del agregado `NotificationTemplate`. Ese desfase es consistencia eventual, y aquí es la respuesta correcta, no un defecto.

## La grieta: concurrencia sobre la raíz

<Callout kind="honesto" title="Este repositorio no tiene bloqueo optimista. Ni uno.">

Búscalo tú mismo: no hay ninguna propiedad `RowVersion`, ninguna llamada a `IsConcurrencyToken()`, ningún `[Timestamp]` en las seis configuraciones de entidad ni en la migración `InitialCreate`. Todas las escrituras siguen el patrón "leer, decidir en memoria, guardar" sin ninguna comprobación de que el estado leído siga siendo el estado actual al momento de guardar. Eso significa que hay al menos una invariante de negocio que el sistema protege perfectamente contra un solo usuario y no protege en absoluto contra dos a la vez.

</Callout>

El escenario concreto, con las clases de este dominio: dos peticiones simultáneas agregan una configuración de canal `Email` al mismo trigger.

Y aquí viene el contraste que hace útil este ejemplo: el **mismo repositorio protege bien la otra regla de unicidad**. `CreateTriggerHandler` comprueba `ExistsAsync(eventKey)` antes de crear, y esa comprobación tiene exactamente el mismo agujero lógico entre lectura y escritura — pero la migración crea `UX_NotificationTriggers_EventKey` como índice **único**. Si dos peticiones ganan la carrera a la vez, la base de datos rechaza la segunda. El índice de configuraciones, `IX_NotificationConfigurations_Trigger_Channel`, es un índice de consulta corriente, no único. Misma forma de código, dos niveles de protección distintos, y la diferencia está en una línea de una migración.

```csharp title="Persistence/Migrations/20260904223406_InitialCreate.cs (dos índices, dos garantías)"
migrationBuilder.CreateIndex(
    name: "UX_NotificationTriggers_EventKey",
    table: "NotificationTriggers",
    column: "EventKey",
    unique: true);            // <- la base de datos SÍ protege esta regla

migrationBuilder.CreateIndex(
    name: "IX_NotificationConfigurations_Trigger_Channel",
    table: "NotificationConfigurations",
    columns: new[] { "NotificationTriggerId", "Channel" });
    // ^ sin 'unique': solo acelera consultas. La invariante de canal único
    //   vive únicamente en la memoria del agregado, durante la transacción.
```

### Las tres formas de cerrarla, con su coste

<ol class="ddd-steps">
    <li>
        <strong>Índice único filtrado en la base de datos.</strong> Un
        <code>CREATE UNIQUE INDEX ... WHERE IsEnabled = 1</code> sobre
        <code>(NotificationTriggerId, Channel)</code> haría imposible el estado inválido, pase lo que pase.
        Coste: la violación llega como una excepción de SQL Server que hay que traducir a un error de
        dominio comprensible, y la regla queda escrita en dos sitios (el agregado y el esquema) que pueden
        divergir. Beneficio: es la única defensa que no se puede saltar.
    </li>
    <li>
        <strong>Token de concurrencia en la raíz.</strong> Añadir una propiedad de versión a
        <code>NotificationTrigger</code> marcada como <code>IsRowVersion()</code>: al guardar, EF incluye la
        versión leída en el <code>WHERE</code> del <code>UPDATE</code> y lanza
        <code>DbUpdateConcurrencyException</code> si alguien la cambió antes. Coste: el token vive en el
        agregado (una propiedad técnica dentro del dominio, que es justo lo que este proyecto ha evitado
        hasta ahora) y hay que decidir una política de reintento. Beneficio: protege <em>todas</em> las
        invariantes de la raíz de una vez, no solo la del canal — incluida cualquiera que se agregue
        mañana.
    </li>
    <li>
        <strong>No hacer nada, conscientemente.</strong> Si en el uso real dos administradores nunca
        configuran el mismo trigger en el mismo segundo, el riesgo puede ser aceptable. Lo que no es
        aceptable es no saberlo. La diferencia entre una decisión y un descuido es que la decisión está
        escrita en alguna parte.
    </li>
</ol>

<Callout kind="advertencia" title="Un segundo escenario, ya presente en la ruta de mensajería">

`RecipientSyncService` ([módulo 4](/ddd/context-map)) hace `ExistsAsync` y, si no existe, crea. Si dos mensajes `UserContactUpdated` del mismo usuario se procesan en paralelo, ambos pueden ver "no existe" y ambos intentar insertar el mismo `Id`. Ahí la clave primaria sí frena el desastre, pero el resultado es una excepción de base de datos subiendo por el consumer, no un caso de negocio manejado. Es el mismo problema con distinto final: *toda* secuencia "consulto y luego decido escribir" es una carrera si no hay una restricción o un token que la cierre.

</Callout>

## Lecturas: por qué el repositorio de agregados no alcanza

El [módulo 11](/ddd/arquitectura) mostró la separación entre comandos y consultas. La parte que la persistencia hace visible es el coste de esa separación cuando *no* se lleva hasta el final. Hoy, las consultas de este proyecto pasan por los mismos repositorios de agregados que las escrituras: `ListNotificationsHandler` pide al repositorio una página de `Notification` completos y después los proyecta a `NotificationDto` en memoria.

```csharp title="Application/Notifications/Queries/ListNotifications/ListNotificationsHandler.cs"
var (items, total) = await _notifications.ListAsync(
    query.RecipientId, query.EventKey, query.Status, page, pageSize, ct);

var dtos = items
    .Select(n => new NotificationDto(
        n.Id, n.EventId, n.EventKey, n.ConfigurationId, n.TemplateId,
        n.TemplateVersionId, n.RecipientId, n.Channel.ToString(), n.Destination,
        n.Status.ToString(), n.ProviderMessageId, n.Error, n.OccurredAt, n.Payload))
    .ToList();
// ^ La proyección ocurre EN MEMORIA, después de materializar agregados completos.
//   Un read model haría el Select dentro de la consulta y leería menos columnas.
```

Eso funciona y es perfectamente razonable a esta escala, pero tiene un precio concreto: para pintar una tabla de 20 filas, SQL Server devuelve todas las columnas de cada notificación — incluido el `Payload` en `nvarchar(max)` — y EF construye 20 agregados completos que se descartan de inmediato. Un *read model* de verdad haría el `Select` a la forma del DTO dentro de la consulta, y el motor solo leería las columnas que la pantalla muestra.

Lo que el código sí hace bien, y conviene notar, es `AsNoTracking()` en los métodos `ListAsync` de los repositorios. Es la mitad barata del argumento: dice explícitamente "estos objetos son para leer, no vuelven a la unidad de trabajo", y evita que el change tracker gaste memoria y tiempo vigilando entidades que nadie va a modificar. Los métodos `GetByIdAsync`, en cambio, no lo llevan — precisamente porque esos sí devuelven agregados destinados a ser mutados y guardados.

<Callout kind="antipatron" title="Errores que vas a cometer al mapear un modelo rico">

- **Abrir un setter "solo para EF".** Nunca es solo para EF: en tres meses hay código de aplicación usándolo. Si EF necesita entrar, se le abre la puerta en la configuración, no en la clase.
- **Olvidar el `ValueComparer` de un tipo mutable convertido.** Los cambios simplemente no se guardan, sin error ni aviso. Es el bug más difícil de esta lista.
- **Cargar la raíz sin sus hijos para "optimizar".** El agregado deja de poder validar su invariante, y el fallo aparece meses después como datos inconsistentes.
- **Dejar que la migración mande.** Si alguien agrega una columna a mano y luego la propiedad al agregado para que "cuadre", el modelo pasó a ser un reflejo del esquema. La dirección correcta es: cambia el agregado, genera la migración, revisa el `Up()`.
- **Suponer que una comprobación en memoria es una garantía.** Es la lección completa de este módulo.

</Callout>
