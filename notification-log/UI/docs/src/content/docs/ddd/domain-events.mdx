<Callout kind="concepto" title="Objetivos de este módulo">

- Definir un evento de dominio y para qué problema existe.
- Verificar, buscando en el código, que el mecanismo existe pero no se usa todavía.
- No confundir un evento de dominio (interno) con un evento de integración (público).

</Callout>

## Concepto

Un evento de dominio es un hecho relevante para el negocio que ya ocurrió, expresado en pasado: `PedidoConfirmado`, `PagoRechazado`. Es el pegamento entre agregados **dentro del mismo contexto**: permite cumplir la regla de "una transacción, un agregado" — el agregado A cambia y publica un evento; un handler reacciona y modifica B, en el mismo servicio. Cruzar la frontera de un bounded context es un problema distinto, que resuelve un evento de **integración**, no uno de dominio — es justo la distinción que cierra este módulo.

<Callout kind="honesto" title="El mecanismo existe. El uso, todavía no.">

`AggregateRoot` ya trae todo lo necesario para levantar eventos de dominio: `Raise`, `DomainEvents` y `ClearDomainEvents`. Pero si buscas en todo el proyecto quién llama a `Raise(...)`, la respuesta es: nadie todavía. Ningún agregado de este dominio levanta un solo evento hoy. Vale la pena decirlo así de directo, porque es exactamente el tipo de detalle que este tutorial se propuso no esconder.

</Callout>

```csharp title="Domain/Common/AggregateRoot.cs (completo)"
public abstract class AggregateRoot : Entity
{
    private readonly List<IDomainEvent> _domainEvents = new();

    public IReadOnlyCollection<IDomainEvent> DomainEvents => _domainEvents.AsReadOnly();

    protected void Raise(IDomainEvent domainEvent) => _domainEvents.Add(domainEvent);

    public void ClearDomainEvents() => _domainEvents.Clear();
}

// Búsqueda en todo el repo de `Raise(`: solo aparece aquí, en la definición.
// Ningún NotificationTrigger, NotificationTemplate, Recipient o Notification lo invoca.
```

## ¿Por qué no hacía falta todavía?

Repasa el [módulo de agregados](/ddd/agregados): la única operación de este dominio que toca dos agregados a la vez (`AddConfigurationHandler` leyendo `NotificationTrigger` y `NotificationTemplate`) solo *lee* el segundo, nunca lo muta. No hay, todavía, ningún caso real en el código donde cambiar un agregado deba disparar una mutación de otro. Los eventos de dominio resuelven un problema — desacoplar la reacción en cascada entre agregados — que este dominio, en su estado actual, no tiene.

## Así se vería si lo necesitaras

Imagina que el negocio pidiera: "cuando se agregue una configuración a un trigger, hay que notificar a un sistema externo de auditoría". Hoy eso obligaría a inyectar ese sistema externo directo en `AddConfigurationHandler`, mezclando dos responsabilidades. Con el mecanismo que ya existe, la solución sería levantar un evento desde el agregado y reaccionar fuera de la transacción principal:

```csharp title="Hipotético: cómo se vería usando el mecanismo existente"
// HIPOTÉTICO — así se vería, no está implementado en el repo actual.

// 1) El agregado levanta el hecho, en pasado, sin saber quién reaccionará:
public sealed record ConfigurationAdded(Guid TriggerId, Guid ConfigurationId, NotificationChannel Channel)
    : DomainEvent;

public NotificationConfiguration AddConfiguration(Guid templateId, NotificationChannel channel)
{
    EnsureChannelIsFree(channel);
    var configuration = NotificationConfiguration.Create(templateId, channel);
    _configurations.Add(configuration);

    Raise(new ConfigurationAdded(Id, configuration.Id, channel));   // <- la línea que falta hoy

    return configuration;
}

// 2) Algo (un interceptor de EF Core, o el propio handler) despacha trigger.DomainEvents
//    después de SaveChangesAsync, y limpia con ClearDomainEvents(). El handler de auditoría
//    externo se suscribe a ConfigurationAdded sin que AddConfigurationHandler sepa que existe.
```

<Callout kind="advertencia" title="Dos trampas del ejemplo de arriba, puestas a propósito">

**El nombre.** `ConfigurationAdded` es el nombre del método en pasado, no un hecho de negocio: nadie de negocio dice "se añadió una configuración". Compáralo con `PedidoConfirmado` o `PagoRechazado` del inicio del módulo. Es el vicio más común al adoptar este patrón — eventos CRUD disfrazados de eventos de dominio, que nombran la operación técnica en vez del hecho que le importa a alguien. En este dominio el candidato con lenguaje ubicuo de verdad está en la ruta de envío: `NotificacionFallida` es un hecho que negocio querría conocer y sobre el que querría reaccionar; "se añadió una configuración", no.

**El momento del despacho.** Despachar después de `SaveChangesAsync` significa que el efecto secundario ocurre *fuera* de la transacción: si el proceso muere entre el commit y el despacho, el evento se pierde sin rastro. Y despacharlo dentro te devuelve el problema de consistencia que intentabas evitar. La salida real es un **outbox** — persistir el evento en la misma transacción que el cambio, y publicarlo después desde un proceso aparte — y es justo la conversación que abre `notification_dispatch_requested.proto`.

</Callout>

<Callout kind="advertencia" title="No confundas las dos cosas">

`UserContactUpdated` (que ya viste en el [módulo de Context Map](/ddd/context-map)) es un **evento de integración**: cruza la frontera de dos servicios, viaja por un bus de mensajería, está versionado con `schema_version` y usa event-carried state transfer. Un **evento de dominio** como el `ConfigurationAdded` hipotético de arriba sería interno a este único servicio, no necesita versión de esquema ni tolerar pérdida de mensajes, y probablemente se procesaría en la misma unidad de trabajo o inmediatamente después. Son herramientas para problemas distintos — este repo ya resuelve el primero; todavía no ha necesitado el segundo.

</Callout>

<Callout kind="ejercicio" title="Ejercicio para pensar">

Busca en tu propio código un lugar donde, después de guardar algo, el mismo método sigue trabajando para actualizar una segunda cosa no relacionada directamente ("guardar el pedido y también actualizar el inventario y también mandar un correo"). Esa cadena de responsabilidades mezcladas en un solo método es exactamente lo que un evento de dominio permitiría separar.

</Callout>
