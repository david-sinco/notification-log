## Concepto

El Context Map documenta cómo se relacionan los bounded contexts. Los patrones más útiles en la práctica:

- **Anti-Corruption Layer (ACL):** traduce el modelo ajeno para que no contamine el tuyo.
- **Open Host Service / Published Language:** un contrato estable que varios consumidores comparten.
- **Customer–Supplier:** el contexto río arriba considera las necesidades del de río abajo.
- **Conformist:** te adaptas al modelo ajeno sin traducir, sin poder de negociación.
- **Shared Kernel:** código de dominio compartido entre dos contextos — potente y peligroso.
- **Separate Ways:** integrar cuesta más de lo que aporta; duplicar es la respuesta correcta.

## El contrato: Published Language

NotificationLog no consume el modelo interno del sistema de usuarios ni sus tablas. Consume un contrato Protobuf versionado, publicado a propósito para varios consumidores — eso es un **Open Host Service** con **Published Language**. El propio archivo `.proto` documenta, en comentarios, por qué está diseñado como un snapshot completo y no como un delta:

```protobuf title="Shared/NotificationLog.Contracts/Users/user_contact_updated.proto"
message UserContactUpdated {
  // Metadata del mensaje en sí (cuándo se generó este snapshot), no del usuario.
  string event_id = 1;
  google.protobuf.Timestamp occurred_at = 2;
  int32 schema_version = 3;

  // Los datos finales del usuario. email/phone vacíos = sin dato confirmado (nunca lo
  // tuvo, o se lo borraron) — las dos cosas se representan igual, a propósito.
  string user_id = 10;
  string name = 11;
  string email = 12;
  string phone = 13;
  bool is_active = 14;
  string locale = 15;
  string time_zone = 16;

  // map, no optional: la ausencia de una clave ya es la forma natural de decir
  // "ya no tiene ese atributo" en un snapshot completo.
  map<string, string> attributes = 17;
}
```

Tres decisiones de diseño de este contrato evitan acoplar a los consumidores a los detalles internos del productor:

- **`schema_version`:** permite evolucionar el contrato sin romper consumidores viejos.
- **Snapshot completo, no delta:** "event-carried state transfer" — si se pierde un mensaje, el siguiente trae todo de nuevo. Ningún consumidor queda permanentemente desincronizado por un mensaje perdido.
- **Sin campos `optional`:** un valor vacío es un dato real ("sin confirmar"), no "no sé". La ausencia de significado ambiguo es, otra vez, lenguaje ubicuo — pero aplicado al contrato de integración, no al dominio interno.

## El Anti-Corruption Layer, en un archivo real

El patrón más valioso de este módulo tiene una implementación exacta en el repositorio: `UserContactUpdatedHandler`. Recibe el mensaje ajeno (el tipo Protobuf generado a partir del `.proto` del productor) y lo traduce a un tipo **propio** de Notifications (`UserChange`) antes de que ninguna regla de negocio lo toque. El modelo del productor nunca cruza esa línea.

```csharp title="Infrastructure/Messaging/Consumers/UserContactUpdatedHandler.cs"
public static class UserContactUpdatedHandler
{
    public static Task Handle(UserContactUpdated message, RecipientSyncService syncService, CancellationToken ct)
    {
        var change = MapToUserChange(message); // Protobuf -> el UserChange de Application
        return syncService.HandleAsync(change, ct);
    }

    // email/phone vacíos ya son un valor con significado (sin dato confirmado), no "no vino" —
    // el mensaje es un snapshot completo, así que se pasan tal cual, sin traducir "" a null.
    private static UserChange MapToUserChange(UserContactUpdated message) =>
        new(
            UserId: Guid.Parse(message.UserId),
            Name: message.Name,
            Email: message.Email,
            Phone: message.Phone,
            Locale: message.Locale,
            TimeZone: message.TimeZone,
            Attributes: message.Attributes.ToDictionary(kv => kv.Key, kv => (string?)kv.Value),
            IsActive: message.IsActive);
}
```

## Un solo comando, no uno por campo

Vale la pena leer el razonamiento detrás de `RecipientSyncService`, porque explica una decisión de Customer–Supplier real: como el mensaje ya llega como snapshot completo, descomponerlo en varios comandos (uno por campo cambiado) habría roto la atomicidad — si el tercer comando fallaba, los dos anteriores ya habrían hecho commit. Con un único comando que aplica todos los campos sobre la misma instancia, la atomicidad sale gratis: un solo `SaveChangesAsync`.

```csharp title="Application/Recipients/Services/Sync/RecipientSyncService.cs"
public sealed class RecipientSyncService
{
    public async Task HandleAsync(UserChange change, CancellationToken ct)
    {
        var exists = await _recipients.ExistsAsync(change.UserId, ct);

        if (!exists)
        {
            var createCommand = new CreateRecipientCommand(
                change.UserId, change.Name ?? "", change.Email, change.Phone,
                change.Locale, change.TimeZone, change.IsActive, change.Attributes);
            await _createRecipient.HandleAsync(createCommand, ct);
            return;
        }

        var updateCommand = new UpdateRecipientCommand(
            change.UserId, change.Name, change.Email, change.Phone,
            change.Locale, change.TimeZone, change.IsActive, change.Attributes);

        await _updateRecipient.HandleAsync(updateCommand, ct);
    }
}
```

<Callout kind="advertencia" title="Por qué esto NO es Conformist">

Sería fácil confundir esto con el patrón *Conformist* ("me adapto al modelo ajeno sin traducir"). No lo es: `Recipient` tiene su propia forma, sus propias reglas (`CanReceive`, normalización de teléfono/email) y su propio ciclo de vida — el mensaje de integración solo lo *alimenta*. Si Notifications simplemente guardara el mensaje tal cual sin una capa de traducción ni reglas propias, ahí sí sería Conformist. La línea que separa ambos patrones es exactamente el ACL de arriba.

</Callout>

<Callout kind="ejercicio" title="Ejercicio para pensar">

Busca en tu propio código un punto donde un mensaje externo (un webhook, un evento de otro servicio, la respuesta de una API de terceros) se deserializa directamente en un tipo que luego viaja hasta tu capa de dominio. Si lo encuentras, esa es la ausencia de un ACL: el modelo ajeno ya cruzó la frontera. Diseña el tipo propio que debería interceptarlo, siguiendo el molde de `UserChange`.

</Callout>
