<Callout kind="concepto" title="Objetivos de este módulo">

- Explicar por qué la interfaz de un repositorio vive en el dominio y no en infraestructura.
- Leer una implementación real de EF Core y ver por qué es `internal`.
- Reconocer una factory como método estático, sin necesitar una clase aparte.

</Callout>

<Callout kind="concepto" title="Concepto: Repositorio">

Un repositorio es una abstracción con semántica de colección para obtener y persistir agregados. Existe uno por agregado, no por tabla. Su interfaz vive en el dominio, su implementación en infraestructura. Nada de `IRepository<T>` genérico con `GetAll()` y `Update()` — eso es un DAO disfrazado. Los métodos deben hablar el lenguaje del negocio.

</Callout>

## La interfaz vive en el dominio, con nombres de negocio

`INotificationTriggerRepository` vive en `NotificationLog.NotificationService.Domain.Triggers` — el mismo namespace que `NotificationTrigger`. Ningún método se llama `FindAll` o `GetByStatusIn(...)`: se llaman `GetByEventKeyAsync` y `ExistsAsync(EventKey)`, porque esas son las preguntas que el negocio realmente hace.

```csharp title="Domain/Triggers/INotificationTriggerRepository.cs"
namespace NotificationLog.NotificationService.Domain.Triggers;

public interface INotificationTriggerRepository
{
    Task<NotificationTrigger?> GetByIdAsync(Guid id, CancellationToken ct);
    Task<NotificationTrigger?> GetByEventKeyAsync(EventKey eventKey, CancellationToken ct);
    Task<bool> ExistsAsync(EventKey eventKey, CancellationToken ct);
    Task AddAsync(NotificationTrigger trigger, CancellationToken ct);
    Task<(IReadOnlyList<NotificationTrigger> Items, int TotalCount)> ListAsync(
        string? search, bool? isEnabled, int page, int pageSize, CancellationToken ct);
}
```

<Callout kind="honesto" title="Los tres primeros métodos son un repositorio. El cuarto es otra cosa.">

`GetByIdAsync`, `GetByEventKeyAsync` y `ExistsAsync(EventKey)` tienen semántica de colección y hablan el lenguaje del negocio. `ListAsync(string? search, bool? isEnabled, int page, int pageSize)` no: `search`, `page` y `pageSize` no son vocabulario de este dominio — son la paginación de una pantalla. Es un método de consulta viviendo en una interfaz del dominio.

Y no es un detalle estético: es la **causa directa** del coste que señala el [módulo 12](/ddd/persistencia) en las lecturas. Como el contrato obliga a devolver `NotificationTrigger` completos, la capa de consulta no tiene más remedio que materializar agregados enteros —con sus configuraciones incluidas— para pintar una tabla de veinte filas.

La separación limpia sería sacar las consultas a su propia abstracción — un `ITriggerQueries` en `Application` que devuelva DTOs directamente — y dejar en el dominio solo los métodos que cargan agregados *para modificarlos*. Es el CQRS del [módulo 11](/ddd/arquitectura) llevado hasta la capa de datos. Este repositorio se queda a medio camino, con un coste razonable a esta escala; lo que no conviene es no saber dónde está la línea.

</Callout>

## La implementación vive en infraestructura, y es invisible fuera de ella

`NotificationTriggerRepository` usa Entity Framework Core directamente — `Include`, `AsNoTracking`, `EF.Functions.Like` — todo el vocabulario de un ORM que jamás debería aparecer en el dominio. Y está marcada `internal`: fuera de `Infrastructure`, nadie puede siquiera nombrar esa clase. La capa de aplicación solo conoce `INotificationTriggerRepository`.

```csharp title="Infrastructure/Persistence/Repositories/NotificationTriggerRepository.cs"
internal sealed class NotificationTriggerRepository(NotificationDbContext db) : INotificationTriggerRepository
{
    public Task<NotificationTrigger?> GetByIdAsync(Guid id, CancellationToken ct)
        => _db.Triggers
            .Include(t => t.Configurations)   // el agregado siempre completo
            .SingleOrDefaultAsync(t => t.Id == id, ct);

    public Task<NotificationTrigger?> GetByEventKeyAsync(EventKey eventKey, CancellationToken ct)
        => _db.Triggers
            .Include(t => t.Configurations)
            .SingleOrDefaultAsync(t => t.EventKey == eventKey, ct);

    public Task<bool> ExistsAsync(EventKey eventKey, CancellationToken ct)
        => _db.Triggers.AnyAsync(t => t.EventKey == eventKey, ct);
}
```

Nota algo más: `GetByIdAsync` y `GetByEventKeyAsync` siempre hacen `.Include(t => t.Configurations)`. El repositorio nunca devuelve un `NotificationTrigger` a medias — siempre carga el agregado completo, con sus configuraciones, porque cargar solo la raíz sin sus hijos rompería la posibilidad de validar la invariante de canal único ([módulo 7](/ddd/agregados)) la próxima vez que alguien llame a `AddConfiguration`. Cómo consigue EF Core rellenar esa colección si `Configurations` es de solo lectura y el campo real es privado se explica en el [módulo 12](/ddd/persistencia).

<Callout kind="concepto" title="Concepto: Factory">

Encapsula la creación compleja de agregados garantizando que nazcan en estado válido. Cuando el constructor requeriría demasiados pasos o conocimiento, se usa un método factoría estático (`Pedido.CrearDesdeCarrito(...)`) o una clase factoría dedicada.

</Callout>

## Factories como método estático, no como clase aparte

Ninguno de los cuatro agregados de este dominio tiene una clase `Factory` separada — y no hace falta, porque cada uno resuelve su creación con un método estático nombrado en el propio agregado. `NotificationTemplate.Create` es el ejemplo más completo: en una sola llamada valida el nombre, valida el canal, y además crea internamente la primera `TemplateVersion` — el agregado nunca existe en un estado "plantilla sin ninguna versión".

```csharp title="Domain/Templates/NotificationTemplate.cs (factory estática)"
public sealed class NotificationTemplate : AggregateRoot
{
    private NotificationTemplate() { }   // EF Core — nunca para negocio

    public static NotificationTemplate Create(
        TemplateName name, NotificationChannel channel, string? subject, string body)
    {
        ArgumentNullException.ThrowIfNull(name);

        if (!Enum.IsDefined(channel))
            throw new DomainException($"El canal '{channel}' no es válido.");

        var template = new NotificationTemplate
        {
            Id = Guid.NewGuid(),
            Name = name,
            Channel = channel,
            IsEnabled = true
        };

        // El agregado nunca existe sin al menos una versión vigente.
        template._versions.Add(TemplateVersion.Create(1, subject, body, channel));

        return template;
    }
}
```

El constructor real (`private NotificationTemplate() { }`) queda reservado exclusivamente para que Entity Framework Core reconstruya el objeto al leerlo de la base de datos — nunca para uso de negocio. Esa es la otra mitad del patrón de fábrica en este código: dos caminos de creación (`Create` para negocio, constructor vacío para el ORM) que nunca se cruzan.

Busca en tu código un repositorio con métodos genéricos (`GetAll`, `FindById`, `Update`) que sirva a más de un tipo de agregado. Divídelo en un repositorio por agregado y renombra cada método con la pregunta real de negocio que responde — igual que `ExistsAsync(EventKey eventKey)` en vez de un genérico `Exists(object id)`.

</Callout>
