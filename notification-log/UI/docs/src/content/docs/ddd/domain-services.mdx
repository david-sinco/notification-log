- Definir cuándo una operación merece salir de un agregado hacia un Domain Service.

## Concepto

Un Domain Service es una operación de dominio significativa que no pertenece naturalmente a ninguna entidad ni value object — típicamente porque involucra varios agregados o requiere una política externa, como un servicio de transferencia entre dos cuentas. Su abuso produce el antipatrón de modelo anémico: toda la lógica en servicios, entidades reducidas a bolsas de datos con getters y setters.

<Callout kind="honesto" title="Este dominio no tiene ni un solo Domain Service — y eso es información útil">

`NotificationLog.NotificationService.Domain` no tiene ninguna clase de servicio. Todo el comportamiento de negocio cabe dentro de sus cuatro agregados (`NotificationTrigger`, `NotificationTemplate`, `Recipient`, `Notification`). Ninguna regla necesitó todavía "salirse" de un agregado — y por eso no se creó ningún servicio de dominio para forzarla a existir.

</Callout>

## Lo que sí existe: Application Services, que no son lo mismo

Hay varias clases que *suenan* a servicio de dominio pero no lo son — `NotificationDispatchService` y `RecipientSyncService`. Viven en `NotificationLog.NotificationService.Application`, no en `Domain`, y esa ubicación no es casualidad: dependen de repositorios, de un renderizador de plantillas y de remitentes por canal — todo interfaces de infraestructura (puertos) que un Domain Service, por definición, no debería conocer.

```csharp title="Application/Notifications/Services/Dispatch/NotificationDispatchService.cs (firma)"
// Notifications/Services/Dispatch — vive en Application, no en Domain.
public sealed class NotificationDispatchService
{
    private readonly INotificationTriggerRepository _triggers;
    private readonly IRecipientRepository _recipients;
    private readonly INotificationTemplateRepository _templates;
    private readonly ITemplateRenderer _renderer;              // puerto de infraestructura
    private readonly IEmailNotificationSender _emailSender;    // puerto de infraestructura
    private readonly ISmsNotificationSender _smsSender;        // puerto de infraestructura
    // ...un servicio de dominio real nunca depende de puertos de envío o renderizado.
}
```

Mira con atención qué hace y qué *no* hace este método. Las decisiones de negocio reales — "¿este trigger está habilitado?", "¿qué configuraciones están activas?", "¿puede este destinatario recibir por este canal?" — están delegadas a los propios agregados (`trigger.ResolveActiveConfigurations()`, `recipient.CanReceive(channel)`). Lo que hace `NotificationDispatchService` es orquestar: buscar, renderizar, enviar, registrar el resultado. Eso es el trabajo de una capa de aplicación, no de un servicio de dominio.

```csharp title="Application/Notifications/Services/Dispatch/NotificationDispatchService.cs (orquestación)"
public async Task DispatchAsync(BusinessEvent businessEvent, CancellationToken ct)
{
    var trigger = await _triggers.GetByEventKeyAsync(EventKey.Create(businessEvent.EventKey), ct);

    if (trigger is null || !trigger.IsEnabled)
        return;   // decisión ya resuelta por el estado del agregado

    var recipient = await _recipients.GetByIdAsync(businessEvent.RecipientId, ct);
    if (recipient is null) return;

    // trigger decide QUÉ configuraciones aplican; el servicio solo itera sobre la respuesta.
    foreach (var configuration in trigger.ResolveActiveConfigurations())
        await DispatchConfigurationAsync(businessEvent, trigger.EventKey.Value, configuration, recipient, ct);
}

private async Task DispatchConfigurationAsync(/* ... */)
{
    // recipient decide si puede recibir; el servicio solo actúa según la respuesta.
    if (!recipient.CanReceive(configuration.Channel))
        return;

    // desde aquí: buscar plantilla, renderizar, enviar, registrar. Pura orquestación.
}
```

## Antes de extraer nada: la misma regla ya está en dos sitios

<Callout kind="honesto" title="Una regla de negocio, dos ubicaciones y dos tipos de excepción">

Antes de plantear un Domain Service, conviene mirar lo que ya hay. La regla "la configuración y la plantilla deben ser del mismo canal" **ya vive en el dominio**: `NotificationTrigger.ChangeConfigurationTemplate` la comprueba y lanza `DomainException`. Pero en el camino de alta, `AddConfigurationHandler` la comprueba otra vez y lanza `AppValidationException`.

Misma regla de negocio, dos ubicaciones, dos tipos de excepción y — vía `GlobalExceptionHandler` ([módulo 11](/ddd/arquitectura)) — dos códigos HTTP distintos para el mismo error, según por dónde entres. Es el tipo de duplicación que no se ve en una revisión de código porque cada mitad, por separado, parece razonable.

</Callout>

El arreglo no es un Domain Service: es darle a `AddConfiguration` la misma firma que ya tiene su hermana, y dejar que el agregado juzgue.

```csharp title="El arreglo real, antes de pensar en extraer nada"
// Domain/Triggers/NotificationTrigger.cs — misma forma que ChangeConfigurationTemplate,
// que ya comprobaba exactamente esta regla y lanzaba DomainException.
public NotificationConfiguration AddConfiguration(
    Guid templateId, NotificationChannel templateChannel, NotificationChannel channel)
{
    if (templateChannel != channel)
        throw new DomainException(
            $"La configuración es de canal {channel} y la plantilla de {templateChannel}.");

    EnsureChannelIsFree(channel);

    var configuration = NotificationConfiguration.Create(templateId, channel);
    _configurations.Add(configuration);

    return configuration;
}

// Application/.../AddConfigurationHandler.cs — el handler deja de juzgar el canal.
if (!template.IsEnabled)   // estado de OTRO agregado: esta comprobación sí se queda aquí
    throw new AppValidationException($"La plantilla '{template.Name}' está desactivada.");

var configuration = trigger.AddConfiguration(template.Id, template.Channel, cmd.Channel);
```

El handler sigue leyendo el `template` —sigue cumpliendo la Regla 4 del [módulo 7](/ddd/agregados), porque solo escribe `trigger`— pero ya no *decide*: le pasa el dato al agregado. En cambio la comprobación `!template.IsEnabled` **sí** se queda en el handler: "esta plantilla está publicada" es estado de *otro* agregado, y `NotificationTrigger` no tiene por qué conocerlo ni podría comprobarlo por sí mismo. Esa distinción — qué dato le pasas al agregado y qué decisión te quedas — es la parte genuinamente difícil de la Regla 4.

## ¿Cuándo aparecería un Domain Service real aquí?

Con el arreglo anterior aplicado, la pregunta del Domain Service se puede plantear bien. Si esa política de compatibilidad creciera — por ejemplo, si empezaran a existir reglas más elaboradas sobre qué plantillas son compatibles con qué triggers, con excepciones y casos especiales que ya no cupieran dentro de `NotificationTrigger` porque necesitaran datos de varios agregados a la vez — ahí sí valdría la pena extraerla a un Domain Service explícito, algo como:

```csharp title="Así se vería (hipotético, no existe en el repo)"
// Domain/Triggers/ITemplateCompatibilityPolicy.cs — HIPOTÉTICO, no existe en este repo.
// Solo tendría sentido si la regla de compatibilidad creciera más allá de dos condiciones.
public interface ITemplateCompatibilityPolicy
{
    void EnsureCompatible(NotificationTrigger trigger, NotificationTemplate template, NotificationChannel channel);
}
```

<Callout kind="advertencia" title="Por qué NO se hizo todavía">

Con dos condiciones simples ("¿está habilitada?", "¿coincide el canal?") —una de las cuales, tras el arreglo de arriba, ya vive dentro del agregado— envolver lo que queda en una clase de servicio de dominio sería sobreingeniería: una interfaz, una implementación y un registro en el contenedor de DI para un solo `if`. Esa es exactamente la advertencia clásica sobre el abuso de Domain Services: produce entidades anémicas y una capa de servicios inflada. La regla práctica es dejar la lógica donde vive hasta que el dolor de tenerla ahí sea mayor que el coste de extraerla.

Y una precisión sobre dónde viviría si algún día se extrajera: un Domain Service que no depende de nada externo **no necesita interfaz ni registro en DI**. Es una clase del dominio, sin más. Reserva la interfaz para cuando la política dependa de algo que el dominio no puede conocer — y en ese momento vuelve a preguntarte si sigue siendo un servicio *de dominio*.

</Callout>
