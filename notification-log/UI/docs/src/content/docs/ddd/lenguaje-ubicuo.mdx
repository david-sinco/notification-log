## Concepto

El lenguaje ubicuo (*ubiquitous language*) es un vocabulario riguroso, compartido entre quien conoce el negocio y quien escribe el código, que aparece **literalmente** en el código: nombres de clases, de métodos, de mensajes de error. Si negocio dice "el evento `transaccion.realizada` dispara una notificación por el canal activo", el código debería poder decir exactamente eso — sin traducir a `type == 3` o a un booleano llamado `flagA`. El coste de no tenerlo se paga en cada bug ("¿qué significa el estado 2?") y en cada reunión ("cuando dices 'trigger', ¿es lo mismo que la fila de `Configuration` en la base de datos?").

## El vocabulario ya vive en el dominio

No hace falta un glosario aparte para empezar: el propio código de `NotificationLog.NotificationService.Domain` ya usa las palabras que usaría alguien de negocio en una reunión sobre este servicio. Mira cómo se valida el identificador de un hecho de negocio:

```csharp title="Domain/Triggers/EventKey.cs"
public static EventKey Create(string value)
{
    if (string.IsNullOrWhiteSpace(value))
        throw new DomainException("El event key es obligatorio.");

    var normalized = value.Trim().ToLowerInvariant();

    if (normalized.Length > MaxLength)
        throw new DomainException($"El event key no puede superar {MaxLength} caracteres.");

    if (!Format.IsMatch(normalized))
        throw new DomainException(
            $"El event key '{value}' debe tener el formato dominio.accion.");

    return new EventKey(normalized);
}
```

Fíjate en un detalle que suele pasar desapercibido: los mensajes de `DomainException` no están escritos para quien programa, son la voz del propio dominio explicando por qué rechazó algo. "El event key es obligatorio", "Ya existe una configuración activa para el canal Email", "La plantilla está desactivada" — cualquiera de esas frases la podría decir alguien de negocio sin saber qué es C#. Esa es la prueba de que el lenguaje ubicuo funciona aquí: el error de validación **es** la regla de negocio, dicha en su propio idioma, no una traducción de ella.

### El nombre del evento describe un hecho, no una plantilla

Compara `EventKey` con lo que *no* hace: no describe un canal, ni una plantilla, ni una prioridad. Su formato exigido — `dominio.accion`, como `pedido.confirmado` o `usuario.email_verificado` — obliga a que el identificador nombre algo que ya ocurrió en el negocio, nunca cómo se va a notificar sobre eso. Esa separación es lenguaje ubicuo aplicado a una decisión estratégica: el "qué pasó" y el "qué se hace con eso" no comparten un mismo nombre, porque tampoco son la misma decisión. Plantilla, canal y condiciones de envío viven aparte, en `NotificationConfiguration` — la verás en el [módulo de agregados](/ddd/agregados).

<Callout kind="ejercicio" title="Ejercicio para pensar">

Abre cualquier método de `Recipient.cs` o `NotificationTrigger.cs` y tapa el cuerpo con la mano. Solo con el nombre del método y sus parámetros, intenta adivinar qué regla de negocio implementa. Si aciertas casi siempre sin leer el cuerpo, el lenguaje ubicuo está haciendo su trabajo. Repite el ejercicio con un proyecto propio que tenga métodos como `ProcesarData()` o `Update(int status)` — la diferencia de esfuerzo es la medida real del lenguaje ubicuo.

</Callout>
