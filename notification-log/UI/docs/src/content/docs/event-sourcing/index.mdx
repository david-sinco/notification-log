La guía de [DDD](/ddd) enseña el modelado táctico sobre un servicio que guarda **estado**: una fila por trigger, una fila por plantilla, y `UPDATE` cada vez que algo cambia.

Esta guía enseña la alternativa sobre el otro servicio de este mismo repositorio: **Rentals**, el portal de arriendos "Llave", donde nada se actualiza nunca. Lo único que se escribe son hechos —`ListingDrafted`, `ListingApproved`, `VisitNoShow`— y el estado que ves en pantalla es un **cálculo** sobre esos hechos.

<div class="ddd-frase">
<strong>La idea entera:</strong> en lugar de guardar <em>cómo están las cosas</em>, guardas
<em>todo lo que pasó</em>. El estado actual se deriva; la historia, no se puede perder porque es lo
único que hay.
</div>

## Por qué este repositorio es un buen sitio para aprenderlo

Porque tiene **los dos modelos, resolviendo problemas comparables, con el mismo equipo y las mismas bases**. Eso convierte cada decisión en una comparación en vez de en una afirmación:

| | Notifications ([guía DDD](/ddd)) | Rentals (esta guía) |
| --- | --- | --- |
| Fuente de verdad | Filas en tablas | **Eventos en un flujo** |
| Motor | SQL Server + EF Core | PostgreSQL + Marten |
| Escritura | `UPDATE` sobre el agregado | `append` de eventos nuevos |
| Lectura | Los mismos repositorios | **Proyecciones separadas** |
| Concurrencia | Sin protección ([módulo 12](/ddd/persistencia)) | Por número de versión, incluida |
| Historia | Se pierde en cada `UPDATE` | Es el dato |

Cuando una página de esta guía dice *"aquí esto se resuelve distinto"*, puedes abrir el archivo del otro servicio y comprobarlo.

<Callout kind="honesto" title="Rentals está incompleto, y esta guía lo dice cada vez que toca">

El portal "Llave" está en construcción. Hoy tiene tres agregados —`Listing`, `Visit`, `Owner`— y hay trabajo pendiente anotado en `notification-log/todo.md`: consultas entre interesado y propietario, favoritos, búsquedas guardadas, reportes de publicaciones.

Además hay un problema real de evolución de esquema que el [módulo 10](/event-sourcing/evolucion) usa como caso de estudio: **los flujos guardados hoy no se pueden reconstruir**, porque contienen eventos de funcionalidades que ya se borraron y porque `ListingDrafted` cambió de forma.

Esta guía no lo esconde. Al contrario: un event store con un evento huérfano es exactamente la clase de problema que no aparece en ningún tutorial y sí aparece en producción.

</Callout>

<Callout kind="concepto" title="Qué conviene traer leído">

Esta guía **no repite** los conceptos tácticos de DDD: da por sabidos agregado, invariante, value object y repositorio. Si alguno te suena flojo, el módulo correspondiente de la guía de DDD está enlazado en el punto exacto donde hace falta.

Los tres que más se usan aquí:

- [Agregados](/ddd/agregados) — el límite de consistencia, que aquí pasa a ser el límite del **flujo**.
- [Domain Events](/ddd/domain-events) — el mecanismo `Raise` / `Apply`, que aquí es el motor entero.
- [Persistencia](/ddd/persistencia) — para comparar la concurrencia con lo que hace Marten.

</Callout>

<Callout kind="concepto" title="Cómo leer cada página">

Misma estructura que la guía de DDD: **objetivos**, **en una frase**, **concepto**, **código real importado del repositorio**, **para recordar** y **comprueba que lo entendiste**. Y los mismos siete recuadros — 💡 concepto, 🧩 código, ⚠️ advertencia, 🚫 antipatrón, ✏️ ejercicio, 🔍 honesto, 📌 resumen.

Los fragmentos de código se importan de los `.cs` reales, así que no pueden quedar desactualizados en silencio.

</Callout>
